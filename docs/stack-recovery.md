# Восстановление стека и сохранённых данных — T18 / №30

Операторская команда [publication-ops.mjs](../tools/publication-ops.mjs)
создаёт согласованную резервную копию PostgreSQL, продуктов и GeoServer.
Нужны Node.js 26.10.0, Docker Compose v2 с `--wait`, закреплённые образы и
права оператора Docker. Команда работает из исходного checkout на Windows
и Linux; проверка на сервере организации остаётся отдельным обязательным этапом.

Копирование останавливает сервисы проекта: согласуйте окно недоступности,
остановите планировщики, внешние загрузчики и операторские команды.
Во время копирования не запускайте новые команды для этого проекта и не меняйте
код, конфигурацию или секреты. По завершении, включая ошибку, команда возвращает
ранее работавшие сервисы в запущенное состояние. Затем выполните `health`.
Незавершённая копия без `backup.json` непригодна для восстановления.

## Подготовка

- Назначьте отдельные каталоги для исходников, копий и внешних секретов.
  Сохраняйте исходный checkout Git и содержимое `data/viewer` для интерфейса,
  включая локальную картографическую основу. Эти ресурсы не находятся в томах
  продуктов. Снимок `runtime/` содержит серверный код и конфигурацию, но не
  заменяет полный checkout с тестами и ресурсами интерфейса.
- Секреты задайте внешним `--env-file`: `POSTGRES_PASSWORD`, `WORKER_PASSWORD`,
  `API_PASSWORD`, `GATEWAY_PASSWORD`, `MOSAIC_PASSWORD`, `GEOSERVER_ADMIN_USER`,
  `GEOSERVER_ADMIN_PASSWORD`. Не задавайте отличающиеся значения в окружении shell:
  окружение имеет приоритет над файлом Compose. Сохраните исходный комплект
  отдельно: архив GIS и datastore содержит привязки к этим секретам.
- Задайте `PUBLICATION_IMAGE`, `PUBLICATION_INPUT_DIR`, `PUBLICATION_EVIDENCE_DIR`,
  `T4_PORT`; исходники `/input` и продукты API `/assets` должны оставаться `ro`.
  Не используйте общие/external тома: команда допускает только
  `<project>_postgres`, `<project>_assets`, `<project>_geoserver`.
- Для рабочего развёртывания согласуйте wall UTC или исторический demo clock,
  сроки хранения и исключения demo. Существующая политика хранится в базе:
  изменение переменной `PUBLICATION_CLOCK` не заменяет её настройку.

## Копирование и проверка

Примеры для Linux shell (на Windows те же аргументы выполняются одной строкой):

```sh
node tools/publication-ops.mjs backup --project hmc-prod --env-file /srv/hmc/secrets.env --directory /srv/hmc-backups/2026-10-25-01
node tools/publication-ops.mjs verify --directory /srv/hmc-backups/2026-10-25-01
node tools/publication-ops.mjs health --project hmc-prod --env-file /srv/hmc/secrets.env
```

Сервисы останавливаются, только база временно запускается для `pg_dump -Fc`,
затем тоже останавливается. После этого копируются тома assets и geoserver.
Это один согласованный снимок: во время копирования нет worker, API и GIS,
которые могли бы менять продукты или каталог. Сохраняются очереди заданий,
манифесты/ревизии, исходные управляемые копии, Zarr/COG, индексы GIS, метаданные
ключей с отзывами, политики доступа, история использования и сроки хранения.
Отдельно сохраняются код/конфигурация `runtime/`, решения выбранного кодировщика
`decisions/`, идентификаторы образов и контрольные суммы.

**Комплект закрытый.** В нём есть настройки GIS и datastore с паролями.
Храните его в зашифрованном хранилище с ограничением доступа; на Linux команда
создаёт каталог с правами 0700 и dump с 0600. На Windows настройте ACL каталога
заранее. Не отправляйте архив в Git, Issues или переносимые отчёты.
Файл внешних секретов и выданные клиентам API-ключи команда не копирует.
Проверка SHA256 обнаруживает повреждение, но не доказывает подлинность копии:
используйте доверенное хранилище. Проверьте перенос на отдельный носитель.

## Восстановление в новый проект

1. Восстановите исходный checkout, локальные ресурсы интерфейса и закреплённые
   образы. При утрате изменённой конфигурации восстановите её из `runtime/config`
   проверенного комплекта; `backup.json` фиксирует все байты серверного runtime.
   Верните исходный внешний комплект секретов. Команда отклонит несовпадающие
   образы, код, конфигурацию и секреты до создания сервисов.
2. Выберите **новое** имя проекта без контейнеров, сетей и томов.
   Исходный проект сохраняется для отката. Подключите прежний источник только
   для чтения; обеспечьте свободный локальный порт. Во время проверки закройте
   внешнюю маршрутизацию к новому проекту.
3. Выполните восстановление:

```sh
node tools/publication-ops.mjs restore --project hmc-recovered --env-file /srv/hmc/secrets.env --directory /srv/hmc-backups/2026-10-25-01
docker compose --project-name hmc-recovered --env-file /srv/hmc/secrets.env --file compose.publication.yaml up --detach geoserver api gateway
node tools/publication-ops.mjs health --project hmc-recovered --env-file /srv/hmc/secrets.env
```

Команда создаёт базу и роли через штатную инициализацию, восстанавливает dump,
assets и GeoServer, возвращает решения кодирования в `PUBLICATION_EVIDENCE_DIR`.
При ошибке команда завершается ненулевым кодом; внешний доступ и worker
автоматически не запускаются. Сохраните закрытый диагностический журнал,
проверьте причину; для повторной попытки используйте новый проект. Удаляйте
неудачный проект только после архивирования и проверки его принадлежности.

4. До открытия доступа сравните сохранённые run/revision/valid time:
   каталог, каноническое значение точки, metadata и байты числовых/native тайлов,
   scoped WMS. Проверьте действующий и отозванный ключи, лимиты и историю
   использования. `/health` сам по себе этих свойств не доказывает.
5. Выполните worker `once` для сохранённой очереди, проверьте статус задания
   через gateway и повторите доставку: прежний delivery должен вернуть тот же
   job ID. После проверки включите планировщик/worker и внешнюю маршрутизацию.
   Для обычного перезапуска используйте `publication-ops.mjs restart` с именем
   проекта и внешним env-файлом, затем проверьте сохранённую выборку.

## Повторная публикация и кеши

Процессные кеши не входят в копию. Новые API-процессы строят числовые тайлы
детерминированно из сохранённых Zarr и манифестов с прежними контрактами,
кодировщиком и CRS. Нельзя подменять кодировщик под прежними URL.
Контракты `contract.v*.json`, `native-display.v*.json` и CRS defaults входят в
снимок runtime. Старые ревизии сохраняют идентичность и правила доступности.

Для прерванного recoverable job восстановите согласованную копию, затем
возобновите обработку штатным `once` или `retry --job` после ремонта причины;
`retry` применим к допустимым неуспешным заданиям, а не к уже опубликованным.
Если продукты опубликованного задания потеряны, восстановите их из копии либо
постройте новую публикацию из сохранённого источника. При наличии только
управляемого `original.grib2` перенесите его в отдельный каталог входных данных,
сверьте SHA256 и подключите каталог как `/input:ro`.
Для нового построения используйте документированный
[submit --recoverable / --rebuild](publication.md#recover-interrupted-deliveries-t6--18).
Новая публикация получает новую ревизию; нельзя обещать сохранение старых URL
при отсутствии их исходных манифестов. Если потеряна база, исходники позволяют
повторно опубликовать прогноз, но не восстановить отзывы ключей и историю
использования: для них нужна резервная копия базы.

Браузерные тайлы используют `private, no-cache`: повторное получение проходит
проверки доступности, истечения и доступа до кеша. Открытый браузер может ещё
показывать уже загруженный кадр; после аварийного отката оператор должен
потребовать перезагрузку клиентов и повторный выбор доступной публикации.
Сервер отвечает 410 для истёкших выборок и 404 для отсутствующих; сохранённый
кеш браузера не даёт права прочитать их заново. При восстановлении старой копии
отзывы и использование **после даты копии отсутствуют**: до открытия внешнего
доступа повторите последующие отзывы из защищённого журнала либо отзовите и
перевыдайте затронутые ключи. Не объявляйте старый snapshot актуальным состоянием.

## Проверка и эксплуатационные условия

[run-stack-restore.ps1](../publication/run-stack-restore.ps1) запускает T6,
проверки T8, копирование и восстановление в независимые тома; затем сравнивает
HTTP-выборки, отзывы, бюджет, retention и usage, возобновляет очередь и
перезапускает восстановленные сервисы. `-Development` использует короткую
публикацию и не заменяет полный прогон. Оба проекта автоматически архивируются
и удаляются; закрытая копия в `data/backups` исключается из portable evidence.

```powershell
powershell -NoProfile -File publication/run-stack-restore.ps1 -Project hmc-publication-t18-acceptance
```

На согласованном Linux-хосте выполните команды копирования/восстановления выше
и те же проверки gateway. При наличии PowerShell 7 можно запустить runner
через `pwsh`; его Linux-совместимость пока не подтверждена. Запишите дистрибутив,
ядро, Docker/Compose, CPU/RAM/диски, UID/права томов, свободное место для dump,
копии и восстановленного стека, время простоя, health и сравнение выборок.
Зафиксируйте отличия от Docker Desktop/WSL2. Нужны согласованный адрес хоста,
доступ оператора, DNS, порты/межсетевой экран, внешний origin, TLS-сертификат,
цепочка, приватный ключ и доверие клиентов. TLS реализуется и проверяется в
[отдельной задаче №33](https://github.com/stepanosokin/hmc-app-prototype/issues/33);
настоящие секреты не включаются в задачи и отчёты. По согласованию владельца
25.10.2026 проверка на сервере выделена в
[отдельную задачу №50](https://github.com/stepanosokin/hmc-app-prototype/issues/50)
с меткой `needs-info` до выделения хоста. №30 принимает локальные процедуры и
проверки; закрытие №30 не закрывает Linux-host gate, A10 родительской №12 или
проверку ёмкости в №31.
