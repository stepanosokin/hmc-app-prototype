# Диагностика публикации и выдачи (T17, №29)

Отчёт доступен оператору через Compose; отдельная административная панель и
публичный диагностический маршрут отсутствуют. Используйте параметры проекта,
файла окружения и Compose из [инструкции публикации](publication.md).

```powershell
docker compose --env-file <environment.env> --project-name <project> --file compose.publication.yaml run --rm --entrypoint python worker -m publication.diagnostics
# Исторические demo-возрасты; часы наблюдения сервисов остаются реальными:
# ... worker -m publication.diagnostics --clock 2026-10-19T07:00:00Z
```

`services` отдельно показывает контрольную сумму доступного исходника, heartbeat
worker (срок 15 секунд; активная блокировка обработки также означает работающий
worker), доступность базы, API и GIS. Worker обновляет единственный атомарный
heartbeat каждые две секунды между заданиями. `publication.available` проверяет
каталог, метаданные и байты числового тайла через шлюз. Потеря исходника или GIS
не означает потерю ранее опубликованных числовых данных. При остановленной базе
или API шлюз возвращает временную недоступность; после восстановления сохраняется
та же публикация. Наличие heartbeat не гарантирует своевременность обработки.

`jobs` содержит максимум 128 незавершённых/ошибочных заданий с `job_id`, стадией,
возрастом и последней опубликованной выборкой; `jobs_truncated` показывает усечение.
`job_counts` даёт полные счётчики. `pending_lag_seconds` — возраст самого старого
неоконченного задания, `last_commit_age_seconds` — время с последнего коммита
публикации, а не задержка производителя. Ожидаемое расписание производителя пока
не задано: эти числа нельзя считать SLA опоздания прогноза. Сначала проверьте
исходник, затем стадию задания и GIS. Для задания используйте существующий
`/api/v1/jobs/<job_id>`; повторяйте только исправленные recoverable-задания по
[процедуре восстановления](publication.md).

API возвращает закрытый `/ops/diagnostics` только во внутренней сети Compose;
шлюз отклоняет этот путь. `tiles.numeric` и `tiles.native` показывают ёмкость,
текущие байты/число записей и накопленные с запуска процесса hit/miss/failure,
байты выдачи и длительность для метаданных и числовых данных. Сбои генерации и
записи кеша считаются отдельно. Это метрики процесса API, сбрасываемые при его
перезапуске, без неограниченных меток на каждую выборку. `storage` показывает
занятые управляемыми файлами байты, лимит и свободное место файловой системы.
Для CPU/RAM используйте `docker stats --no-stream` для контейнеров своего проекта;
измерения не устанавливают производственную пропускную способность.

Шлюз пишет структурированный JSON с `request_id`, `job_id`/`selection`,
run/revision, статусом, временем и байтами. API пишет тот же `request_id` с
идентичностью поля; worker — начало, стадии и завершение задания с `job_id` и
результирующей выборкой. Ошибки worker содержат только класс исключения.
Произвольные URL, query, заголовки авторизации и тексты исключений в эти события
не включаются. Не архивируйте файлы окружения, ключи и полный `docker inspect`.

Диагностические логи каждого сервиса ограничены тремя файлами по 5 МБ;
heartbeat перезаписывается, метрики остаются фиксированным набором счётчиков.
`usage_retention_days` и `usage_storage.bytes` показывают политику и размер
существующего учёта. Ежедневно выполняйте `python -m publication.budgets collect`
в контейнере worker; изменение срока — `retention --days <1..365>`.
Сборка учёта сохраняет активные backend-резервации: зависшее задание сначала
диагностируют и завершают по [инструкции бюджетов](budgets.md).

В браузере различайте три этапа: HTTP-ошибка загрузки (статус и `X-Request-ID`
в Network), неверные байты/маска или размер блока при декодировании, затем
недоступный WebGL 2/точность шейдера или ошибка загрузки GPU. Сетевой отказ
сопоставляйте с журналом шлюза, декодирование — с encoding/размером из `native.json`,
GPU — с русским сообщением интерфейса и возможностями устройства. Серверные
метрики не устанавливают исправность GPU; принятые браузерные измерения и
ограничения описаны в [инструкции viewer](../viewer/README.md).

Повторяемые упражнения с реальным исходником и закреплёнными сервисами:

```powershell
./publication/run-diagnostics.ps1 -Project hmc-publication-t17-example -Port 8191
# Во время разработки: -Development (сроки +1/+3 ч вместо полной истории T5).
```

Runner использует копию исходника, изолированные тома, явные demo-часы и
доказательства выбора движка T4. Он проверяет T5, затем убирает исходник,
останавливает worker/API/GIS/базу и внедряет отказы генерации/кеша. Проверяет
неизменность тёплого тайла при частичных отказах, недоступность при потере API/базы
и восстановление. Результаты и журналы каждой попытки сохраняются в
`data/reports/t17/<project>`, затем runner автоматически архивирует и удаляет
только свой проект по [процедуре очистки](development/cleanup.md).
Исторические данные, общий кеш Docker и пользовательские проекты сохраняются.
