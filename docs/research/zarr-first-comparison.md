# Zarr-first baseline compared with COG publication

Research date: 2026-10-19. Advisory comparison for wayfinder ticket 07. No installation, sample decoding, benchmark, prototype or external publication was performed. Sources were read directly; mutable documentation/source snapshots do not constitute a tested dependency lock.

## Constraints supplied by the planning discussion

Tens of models, GB-scale files and 15-minute/hourly updates are the planning envelope, with fewer than 100 users; these are not measured capacity requirements. Retain application-managed runs for seven days by reference time, configurable toward 30 days; retain forecast steps beyond that window when their run remains eligible. Organization file-server sources remain read-only. Default to the newest usable run, including validated partial runs; keep the selected run while changing valid time, expose gaps and allow older-run selection. QGIS map display, time selection and identify are required. Bulk numeric downloads are outside the current prototype. Server sizing and latency targets remain open.

## Three concrete candidates

| Candidate | Proposed processing and serving route | Benefit to investigate | Cost/risk to prove |
| --- | --- | --- | --- |
| Zarr-first | ecCodes/AEC decode -> compatible CF-described numeric Zarr assets -> catalogue/provider -> xarray-backed dynamic maps/tiles and xpublish-wms adapter; domain API selects run/revision and returns point values | Array semantics support future time/level/subset APIs without converting everything to individual raster files | QGIS WMS interoperability, dependency compatibility, provider/publication glue, low-zoom reads and chunk/object counts |
| COG baseline | Same decoder -> lossless numeric COG slices/overviews -> GeoServer ImageMosaic/WMS and browser tiles; domain catalogue/API | Existing documented mosaic time/custom dimensions and harvesting; spatial overviews | Conversion/overview cost, catalogue-to-mosaic consistency, run/time client mapping and numerical identify |
| Hybrid | Zarr as normalized numeric data; selected frequently requested fields/steps also become COG for GeoServer | Can retain array-oriented internals while providing established GIS-facing raster route | Two product pipelines, extra bytes/CPU, double availability/cache bookkeeping; derive only justified products |

All three preserve original GRIB bytes or a verified retrievable source reference plus checksums, source revision and processing provenance. A local source copy has a separate capacity cost. Lossless compression does not prove float32 conversion preserves all decoded precision; choose dtype against explicit tolerance. Keep units, masks, native-grid coordinates, surface codes, reference time, lead/validity interval and statistical meaning. Display pixels/overviews are not a numerical reference.

## Documented Zarr-first capabilities and unresolved integration

Zarr specifies chunked arrays, not meteorological or geographic meaning. Use CF coordinate/units/missing-value and grid-mapping conventions alongside original GRIB metadata. A run provider can expose one run at a time with valid time as the temporal axis and reference time as retained metadata, avoiding an ambiguous two-time WMS layer. This is a proposed mapping; CF metadata alone does not establish service/client behavior. [CF 1.12 conventions](https://cfconventions.org/Data/cf-conventions/cf-conventions-1.12/cf-conventions.html).

`titiler.xarray` documents Zarr variable discovery, geographic information and dimension reduction through `bidx` or `sel=dimension=value`, with rendered raster output. This is a concrete browser-serving candidate; it is not proof of WMS/QGIS temporal and identify support. A manifest composed of many stores needs a provider/resolver; stock URL access to one Zarr store does not automatically read our proposed manifest. [TiTiler Zarr example](https://developmentseed.org/titiler/examples/notebooks/Working_with_Zarr/).

TiTiler release notes list 2.4.0 on 2026-09-21 and support for Zarr-Python >=3 since 0.21.1. A Python library major version does not establish support for every Zarr storage format, codec or metadata convention. [TiTiler releases](https://developmentseed.org/titiler/release-notes/).

Xpublish supports dataset-provider plugins loading datasets on request. That gives a place to resolve a catalogue revision and return a compatible xarray dataset, but it does not implement our revision lifecycle or authorization automatically. [Xpublish providers](https://xpublish.readthedocs.io/en/latest/getting-started/tutorial/dataset-provider-plugin.html).

The xpublish-wms README documents CF latitude/longitude coordinates with optional time/vertical and regular lat/lon support tested with GFS. This fits the sample's preliminary grid description; the sample itself remains undecoded. [Plugin README](https://github.com/xpublish-community/xpublish-wms#dataset-requirements).

The inspected query model includes WMS 1.1.1/1.3.0, GetCapabilities, GetMap, legend and GetFeatureInfo. Map queries accept EPSG:4326/3857, time/elevation and tile selection. Identify accepts EPSG:4326 and x/y; no i/j aliases were visible. Thus advertised WMS versions must not be read as tested QGIS compatibility. [Query source](https://github.com/xpublish-community/xpublish-wms/blob/main/xpublish_wms/query.py).

The inspected identify implementation returns CoverageJSON, contains an unimplemented `info_format` comment, computes coordinates from bbox/pixel indices and chooses nearest time for a single requested timestamp. Verify axis order, image row orientation, pixel centres, selected forecast time, format negotiation and no-data behavior; adaptation may be necessary. It must not silently fill a missing forecast time with another time. [Identify source](https://github.com/xpublish-community/xpublish-wms/blob/main/xpublish_wms/wms/get_feature_info.py).

PyPI currently presents 0.13.2 as the available release, while 0.13.3 is yanked as broken. The source requirements specify `xpublish>=0.4.0` with unbounded xarray and several rendering dependencies. Those declarations are not evidence that the newest versions work together, particularly as current Xpublish docs include DataTree behavior. Pin and prove the actual environment; do not select an untested latest-everything stack. [PyPI release record](https://pypi.org/project/xpublish-wms/), [requirements](https://github.com/xpublish-community/xpublish-wms/blob/main/requirements.txt).

A decoder view also needs explicit time normalization: cfgrib commonly exposes scalar reference `time`, forecast `step` and `valid_time`. The WMS serving view should use valid time as its CF temporal axis while preserving forecast reference time/run identity. Treating the scalar run timestamp as the valid-time axis would mislabel every forecast frame. This is a proposed adaptation of the documented coordinate layout. [cfgrib coordinate examples](https://github.com/ecmwf/cfgrib).

## Storage-format compatibility decision

Zarr v2 and v3 have distinct metadata and codec representations. Pin `zarr_format` explicitly, numeric dtype, compression/filter chain, dimension metadata, masks and reader settings. Verify writer -> xarray provider -> tiler -> point API on that exact chain. v2 is a legitimate conservative initial candidate if it reduces integration risk; v3 is a candidate when its features and selected readers are proved useful. Neither is automatically faster. [Zarr v2 specification](https://zarr-specs.readthedocs.io/en/latest/v2/v2.0.html), [Zarr v3 core](https://zarr-specs.readthedocs.io/en/latest/v3/core/index.html).

Consolidation reduces metadata reads, but the Zarr-Python documentation labels v3 consolidated metadata experimental. Rebuild and publish metadata with the same revision as the data it describes; never assume a stale consolidated view will refresh itself. [Consolidated metadata](https://zarr.readthedocs.io/en/stable/user-guide/consolidated_metadata/).

For GeoServer, documented ImageMosaic configuration supports temporal and custom dimensions; REST documents harvesting added granules. Local GeoTIFF reading and the community remote-COG reader are different deployment choices. This research has not established stock GeoServer reading Zarr; do not design on that assumption. Publication into an independently updated mosaic index also needs a consistency design. [ImageMosaic configuration](https://docs.geoserver.org/stable/en/user/data/raster/imagemosaic/configuration/), [harvesting](https://docs.geoserver.org/main/en/user/rest/imagemosaic/), [community COG reader](https://docs.geoserver.org/main/en/user/community/cog/cog/).

## Incremental immutable publication without whole-run copying

Proposed first Zarr design: keep run-level catalogue entries, but store new valid-time/lead batches as independent immutable Zarr assets, partitioned further by compatible grid/level structure when needed. Each contains numeric arrays plus coordinate metadata. Write/validate a new batch off the serving path; add references to a new small immutable run manifest, then publish its revision pointer. A correction replaces only affected asset references; unchanged batches are reused. No multi-GB run copy is required for every 15-minute revision. Coordinate duplication and opening many stores are measurable costs.

For WMS, a custom dataset provider resolves one manifest revision and constructs a lazy xarray view over its available batches, using exact grid/coordinate validation and controlled concatenation. Xarray supports concatenation, but some `different` comparison settings can load payloads; this proposed provider must avoid accidental eager reads and benchmark its metadata/task overhead. For browser tiles, a domain resolver may select a single batch store directly. This is application code, not an out-of-box TiTiler/Xpublish feature. [Xarray concat](https://docs.xarray.dev/en/stable/generated/xarray.concat.html).

An alternative is write-once chunks in a fixed per-run array with an external availability manifest. It avoids separate batch stores, but requires strict chunk ownership, immutable published chunks, fixed reader metadata/revision behavior and tests that readers never access unpublished chunks. Normal `append_dim`/`region` writes are not MVCC. Xarray documents eager metadata writes even with deferred data, unsafe overlapping writes and remaining races despite chunk alignment; do not mutate a public store and infer atomicity from a catalogue transaction. [Xarray to_zarr](https://docs.xarray.dev/en/stable/generated/xarray.Dataset.to_zarr.html).

For all candidates, make assets durable before catalogue publication; resolve revision once per request, include it in cache keys and retain prior assets while referenced. Define how a pinned session refreshes availability within its selected run. Reject missing requested steps explicitly. Do not let a nearest-time WMS default contradict the domain policy. Expire runs by reference time, then delete unreferenced batches/COGs/caches after active readers finish. Keep per-run grouping rather than one giant cross-run cube: deletion and overlapping forecast validity are simpler to reason about. This is a design inference, not an automatic format capability.

## Chunking and amplification: fair hypotheses

A starting experiment for a regular numeric field is time chunk 1, level chunk 1 and spatial chunks such as 256 or 512 cells per side, adjusted to grid dimensions and storage. These are benchmark parameters, not recommended final sizes. Tiny chunks increase file/inode or object-request and metadata overhead; large chunks increase decompression/read amplification for small areas. Count coordinate chunks and batch metadata as well as weather variables.

Time chunk 1 suits individual map frames, but a point series may read one spatial chunk for every time step, much like a series across individual COG slices. Longer time chunks can improve temporal locality while forcing single-frame requests to read other times and complicating incremental ownership. Grouping multiple levels has the same tradeoff for level changes versus one-level maps. Immutable per-time batches deliberately defer cross-time storage optimization; if later API demand justifies it, compact sealed runs into a new optional layout without deleting data still referenced by active revisions.

Low-zoom Zarr rendering may read a large fraction of a full-resolution field. Measure pyramids, coarsened products and tile caching rather than assuming spatial chunks equal COG overviews. COG overview generation has upfront CPU/storage costs, and point queries must bypass averaged overview values. Sharding can reduce object counts but introduces a larger update/ownership unit and reader-codec compatibility requirements; it is not a default remedy. [Zarr sharding specification](https://zarr-specs.readthedocs.io/en/latest/v3/codecs/sharding-indexed/index.html), [GDAL COG overview creation](https://gdal.org/en/stable/drivers/raster/cog.html).

## Proof gates and conditional recommendation

1. Decode all supplied CCSDS messages; verify units, surface identity, masks, orientation and coordinate/value samples. Preserve an agreed numerical reference for every candidate.
2. Build a reproducible dependency lock and tiny v2/v3 compatibility fixtures in the implementation effort. Validate storage readers, codec chain and CF/CRS interpretation end to end; do not infer this from package version bounds.
3. Prove real target-QGIS GetCapabilities, map, temporal selection, explicit run selection, identify, legends and authentication. Include WMS1.1.1/1.3.0 axis/pixel conventions, EPSG4326/3857, absent times and no-data. An adapter must fail this gate visibly if patching cannot meet scope.
4. Demonstrate a late/corrected batch, retry, process crash before/after manifest publication and readers pinned to old revisions. Establish no mixed runs and no unpublished data. For COG/GeoServer, test index updates and cache visibility just as rigorously.
5. Compare representative production runs under simultaneous ingest and cold/warm map, low-zoom, click and short-series requests. Measure p50/p95 latency, CPU/RAM, source bytes, chunk/object/inode counts, peak temporary/final bytes, write amplification, queue freshness, worker concurrency and retention cleanup. Test 7 and 30-day retention envelopes. GB input size and under-100 user count alone do not determine capacity.

Zarr-first deserves a first-class feasibility spike because it keeps a multidimensional numeric model and incremental batches can avoid rewriting complete runs. It should be selected only if reader compatibility, QGIS WMS behavior and publication/low-zoom costs pass the gates. COG/GeoServer remains a credible candidate when GIS interoperability and spatial serving are decisive; hybrid is useful if Zarr internals prove valuable but the WMS adapter does not. No evidence currently establishes Zarr as smaller/faster or COG as the universally cheaper option. The user has not selected an architecture; this comparison supplies the evidence and explicit implementation risks for that decision.
