# Измерения нагрузки T19

Задача: [№31](https://github.com/stepanosokin/hmc-app-prototype/issues/31).
Это процедура измерений. [Итоговый отчёт](evidence/t19/final-report.md) содержит
82 публикации и сокращённую пользователем программу: пять финальных профилей,
исторические 50/100 отдельно, отменённые повторы и промахи целей сохранены.
Родительская задача №12 и завершённая карта работ не меняются.

## Предпосылки

25.10.2026 пользователь выбрал прежний локальный хост Windows / Docker Desktop /
WSL2, входы `data/grib` и поручил выбрать цели по мощности хоста. Наблюдались
24 логических CPU и 33 160 335 360 байт памяти Docker. Сеть — loopback.
Цели для трёх проекций и ограничения контейнеров записаны до измерений в
[`trials/workload-agreement.json`](../trials/workload-agreement.json).
Физический Android по указанию пользователя перенесён в
[№51](https://github.com/stepanosokin/hmc-app-prototype/issues/51).
Текущая приёмка №31 включает desktop Chrome/Edge; перенос не подтверждает Android.
Согласование [T3](adapter-comparison.md) относится только к прежним point/metadata
запросам. Оно не задаёт цели числовых тайлов, графика точки или GPU.

Получены 82 файла ENA по 120 006 204 байта, всего 9 840 508 728 байт;
один расчёт 21.10.2026 06 UTC, 82 срока, 30 сообщений на файл, сетка 2000×1000,
rotated_ll. Нейтральное имя модели — `GRIB-4-1` по кодам центра и процесса.
Проверены метаданные и числовое декодирование всех 2460 сообщений ENA и
24 сообщений ICON; SHA256 каждого файла записан в
[инвентаризации](evidence/t19/final-inventory/inventory.json).
Частота эксплуатационных расчётов и исправлений не известна: расчёты хранения
должны содержать явные сценарные допущения. Два доступных продукта не представляют
любую будущую смесь моделей. Каждый вход сохраняется отдельно; контроль не дублируется
для имитации многогигабайтного обновления.
Доступный контрольный ICON-EU T_G занимает 26 658 586 байт. Он проверяет
корректность, но не представляет требуемый объём или набор полей.
Не подменять репрезентативные обновления повторением этого файла.

Пользователь согласовал расширение прежнего [операторского профиля](grib-crs.md)
на весь набор. Новый явный профиль `grib2-fields` сохраняет код величины, уровень,
единицы, время, статистическую операцию и границы интервала. Неизвестные коды и
единицы остаются неизвестными. Канонический Zarr хранит точные исходные числа;
float32 COG и числовая доставка имеют отдельный записанный допуск в единицах поля.
Прежний строгий профиль контрольной температуры сохраняется.

По дополнительному поручению ветер показывается движущимися стрелками. Пара U/V
должна совпадать по расчёту, редакции, сроку, уровню, сетке, member и ориентации.
Компоненты относительно повёрнутой сетки переводятся в восток/север, затем в
выбранную проекцию. Скорость движения стрелок служит отображению потока;
это не прогноз траекторий. В текущем графике точки явно показана компонента U.
Стрелки не заменяют числовой ряд и не выводятся из цветов изображения.
Поля модели выбираются правыми кнопками групп с вложенными показателями и
уровнями. В списке расчётов остаются только редакции выбранного поля. Отдельная
браузерная проверка проверяет эти элементы и выбранную точку на четырёх размерах
экрана; она выполняется до сброса кеша нагрузочных профилей.
Для слоёв показываются обе реальные границы: облачность 0–400 гПа,
400–800 гПа и 800 гПа — поверхность. Значения давления из GRIB в Па
переводятся в гПа только в подписи; канонические числа и идентичность поля
не меняются. Неизвестные типы поверхностей сохраняют код и исходный масштаб.
Источник кодов — [таблица поверхностей GRIB2](https://codes.ecmwf.int/grib/format/grib2/ctables/4/5/).

Испытывать завершённые функции смены срока и канонического ряда точки из
№39/№41. Сохранить отмену T26: нормативы 100 мс и холодные 3 с для навигации
по времени не использовать. Новые цели нельзя назначить задним числом.

## Матрица и порядок

Для каждого профиля 1/10/50/100 клиентов отдельно записать число HTTP-запросов,
реальных браузеров, длительность, повторы, seed, паузы пользователя и частоту
обновлений. HTTP-клиент не измеряет стоимость отрисовки.

| Измерение | Условия | Сохраняемые результаты |
| --- | --- | --- |
| Сервер и публикация | Карта/клики одновременно с ingestion; холодные и прогретые запросы | Время загрузки, задержка публикации через gateway, очередь, CPU/RAM/I/O, временные и конечные байты |
| Числовая доставка | Числовые тайлы и кешированное цветное изображение для одинаковой выборки и области | p50/p95/p99 успешных ответов, их число/с, ошибки, байты, генерация, попадания в кеш |
| Браузер | Chrome/Edge desktop; Android отдельно в №51; Mercator, строгая ортография, EPSG:3576 | Декодирование, загрузка текстур, время кадра/FPS, память, pan/zoom, повторная смена проекции |
| Навигация по времени | Повторная смена срока во всех трёх проекциях одновременно с ingestion | Холодные/прогретые задержки, атомарность кадра, неизменность карты/камеры/точки, ошибки, отсутствие устаревшего результата |
| Ряд точки | Реальный канонический ряд, частичная ошибка и повтор, смена срока и идентичности выборки | Число/байты/задержки запросов; переиспользование ряда; пропуск/nodata/ошибка/expiry; числовая идентичность |
| Ресурсы клиента | Повторы, вытеснение, потеря контекста, уход со старой проекции | Управляемые массивы/кеш/текстуры/framebuffer вместе ≤128 МиБ, освобождение, ограничение предзагрузки, отсутствие роста |

Записать браузер/версию, устройство/GPU и возможности WebGL, viewport/DPR, zoom,
сеть, кодирование тайла, серверные лимиты и фактические образы контейнеров.
Прямые счётчики памяти и оценки указывать отдельно; отсутствие GPU-счётчика
не означает нулевую память. Числовые допуски остаются обязательными под нагрузкой.

Холодный процесс, пустой серверный кеш и пустой браузерный кеш — разные условия.
Перезапуск контейнера не очищает кеш ОС. Не очищать общие кеши хоста.
Для каждого измерения сохранить точную процедуру прогрева/сброса и объём выборки.
Малое число холодных первых запросов не образует достоверного p99.
Ошибки, отмены и ожидаемые отказы учитывать отдельно от успешной пропускной
способности. Метод расчёта процентилей и границы интервала измерения фиксировать.

## Хранение на семь и 30 дней

Для каждого класса отдельно измерить исходные копии, Zarr, выбранные COG/обзоры,
staging, старые редакции, числовые metadata/тайлы и кеш изображения.
Если появятся серверные производные проекций, добавить их генерацию, readiness,
версионные ключи кеша, предельный размер и хранение. Текущий путь не заменять
другим только для улучшения результатов.

Таблица расчёта должна содержать измеренные байты одной публикации и обновления,
число расчётов/сутки по моделям, долю исправлений, время удержания редакций,
одновременный staging и предел кеша. Отдельно показать постоянное хранение и пик
при публикации/очистке. Для каждого итога на семь/30 дней записать формулу и
допущения. Умножение измеренного образца на число дней — оценка,
а не измеренный многосуточный объём. Учитывать фактическое переиспользование
партий; не складывать общий объект повторно для каждой редакции.

## Воспроизведение и границы существующих команд

Нагрузочный runner использует отдельные контейнеры и тома, фиксированный образ,
лимиты ресурсов, явные часы и новые имена проектов для каждой попытки:

```powershell
docker build -f Dockerfile.publication -t hmc-publication:t19-local .
# Development: три настоящих ENA файла, один HTTP-клиент; это не финальная приёмка.
./tools/run-workloads.ps1 -Project hmc-publication-t19-probe1 -Image hmc-publication:t19-local -Development
# Полная матрица: все 82 ENA файла, 1/10/50/100 клиентов, три повтора.
./tools/run-workloads.ps1 -Project hmc-publication-t19-complete1 -Image hmc-publication:t19-local
```

Каждый повтор отдельно сочетает холодный/прогретый серверный кеш и
числовую/цветную доставку. Для холодного профиля перезапускается API;
для прогретого выполняется проход по закреплённому корпусу. Кеш ограничен LRU:
название прогретого профиля не гарантирует попадание каждого запроса. Состояние
кеша берётся из `access.usage` по gateway `X-Request-ID`: gateway не передаёт
внешнему клиенту backend-заголовок `X-HMC-Cache`. Корреляция выполняется после
измеряемого HTTP-интервала порциями до 1000 идентификаторов; покрытие и ошибки
наблюдения записываются отдельно. Отсутствующая запись не считается попаданием.
Общий кеш ОС не очищается. Каждый браузер использует
новый профиль; его кеш не выдаётся за прогретый. Репрезентативное скалярное поле
ENA одинаково в числовом и цветном вариантах; ветер измеряется отдельно.
HTTP-нагрузка работает минимум заданное время и до завершения браузерного сценария,
с пределом 1800 с. Реальное пересечение с ingestion нужно проверить по UTC-границам
запросов и истории заданий. Один запуск worker не является доказательством
одновременного ingestion во всей матрице.

Другие команды проверяют корректность отдельных функций:

```powershell
# Ресурсы не создаются: проверка сохранённого сравнения и других исторических архивов.
python -B tools/check_evidence.py
# Реальный образец +1/+3 ч с пропуском +2 ч; overlap нужен сценарию Updates.
./tools/run-weather-viewer.ps1 -Project hmc-publication-t13-t19-navigation -Final -WithEdge -Navigation -TimeSwitch -Updates
# Отдельный полный ряд 24 сроков, без искусственного пропуска +2 ч.
./tools/run-weather-viewer.ps1 -Project hmc-publication-t13-t19-series -Final -WithEdge -PointSeries
```

Браузерные команды выполняются последовательно и требуют подготовленных
зависимостей и свободных портов из
[инструкции viewer](../viewer/README.md). Для каждого запуска нужно новое имя
проекта. Физический Android проверяется отдельно по
[браузерной процедуре](development/browser.md). Эти команды не являются
нагрузочным сценарием T19: в них нет утверждённой матрицы клиентов, одновременного
ingestion и эквивалентного cached-image baseline. Для повторяемой нагрузочной
матрицы используется отдельный `run-workloads.ps1` выше.

Перед испытанием заморозить входы по [процедуре приёмки](development/acceptance.md),
сохранить SHA256 исходников, конфигурации, зависимостей, корпусов запросов и данных.
После каждого запуска, включая неудачный, архивировать отчёты и проверить
[очистку](development/cleanup.md). Хранить каждый запуск отдельно; сохранять
пользовательские стенды и общие кеши. Локальная интеграционная проверка не
подтверждает эксплуатационный размер хоста или SLA для 100 клиентов.

Исторический [результат T3](evidence/t3/validation.md) и
[выбор числового адаптера](adr/0001-numerical-http-adapter.md) сохраняются.
Его числовые point/metadata результаты не доказывают эффективность тайлов/GPU.
Состояние подготовки: [T19, 25.10.2026](evidence/t19/preparation.md).
