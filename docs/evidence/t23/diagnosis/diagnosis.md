# T23: диагностика открытых критериев

Дата исследования: 20.10.2026. Задача [№35](https://github.com/stepanosokin/hmc-app-prototype/issues/35)
проверена через GitHub: `open`, отмечены 2/3/4/6/7; открыты 1/5/8.
Это диагностика незавершённой реализации, не новая полная приёмка и не исправление.
Рабочая реализация продолжения T23 и исторические свидетельства сохранены.

## Воспроизводимые симптомы

Команда `python tools/diagnose-t23-cold.py` проверяет SHA256 выбранных архивных
отчётов и бюджет 3000 мс. Два запуска дали exit 1: все семь видов превышают
порог, 3059–5653 мс. [Результат](cold-replay.json) — повторная проверка
сохранённых измерений, а не свежая браузерная загрузка. Скрипт принимает
`--root`, поэтому следующий архив можно проверить тем же условием.

Команда `node tools/diagnose-t23-rotation.mjs` исполняет настоящий модуль
`interaction.js` с записывающим viewer и минимальным DOM. Два запуска дали
exit 1: после pointerdown и десяти pointermove центр остаётся (20°,50°),
вызовов viewer.show нет; после pointerup — один вызов, центр (0°,50°).
[Результат](rotation-dispatch.json) содержит SHA256 исполняемого модуля.
Это проверка обработчика, без браузера, trusted gesture и GPU. Она показывает
причину отсутствия обновления центра во время жеста, но не доказывает
согласованное изображение после будущего исправления.

## Ранжированные гипотезы и границы измерения

До профилирования сформулированы три различающих предположения:

1. HTTP/сервисные операции преобладают: доставка поля остаётся медленной без
   браузера, а непосредственная генерация блоков существенно короче.
2. Задержка накапливается в двух параллельных загрузчиках 18 блоков: временная
   шкала показывает последовательные волны. Это проверяет накопление времени,
   но без отдельного изменения concurrency не доказывает ускорение от его роста.
3. Преобладает подготовка карты: поле заканчивает загружаться значительно
   раньше первого показа. Сохранённые измерения этого не подтверждают.

[Разбор семи видов](timing-breakdown.json): field load составляет 94–97%
navigation-to-first-show, сам превышает 3000 мс в шести случаях. Его границы
включают reference, metadata, блоки, проверку значений, ожидание подготовленного
слоя и incremental uploads. Поэтому это не чистый сетевой таймер. Разность
cold и load тоже не является независимым чистым временем карты: начало load
позже navigation, карта готовится параллельно. В профиле dev3 decode занимал
10,7 мс суммарно, upload с gl.finish — 1,8 мс; оснований считать их главным
объяснением нескольких секунд нет. Источник —
[предыдущая валидация](../continuation/validation.md).

## Свежий профиль реального сервисного пути

Команда подготовки и измерения:

```powershell
powershell -NoProfile -File tools/diagnose-t23-service.ps1 -Project hmc-publication-t23a-diag2 -Image hmc-publication:t23 -Port 8137
```

Использованы тот же SHA256 реального GRIB и publication image, gateway/API,
нативный контракт, 18 блоков по 332820 байт и concurrency=2. Перед HTTP-пробой
API/gateway перезапущены: их field/payload caches холодные, код reader загружен
при старте сервиса. ОС/дисковый кеш не сбрасывался. Браузер, Wi-Fi, GPU и карта
исключены. Проверка native HTTP прошла 4/4 в обеих попытках.

| Проба | Первый metadata + 18 blocks | Повторная последовательность |
| --- | ---: | ---: |
| diag1, диагностическая попытка с дрейфом входов | 4149 мс | 3945 мс |
| diag2, неизменные 117 входов | 4359 мс | 3747 мс |

Источник — [HTTP-отчёт diag2](attempts/diag2/reports/diagnose-http.stdout.log).
Обе свежие последовательности превышают 3000 мс ещё без браузера. Повторная
доставка всего поля не является прежним warm-mode-switch: при переключении
режима браузер переиспользует уже загруженные блоки и не запрашивает их заново.

Отдельный вызов настоящих native-функций без HTTP/IPC дал в diag1 около
309/346 мс на 18 блоков. Это другой cache/profile scope: нельзя арифметически
вычесть его из HTTP wall time и назвать остаток точным временем gateway.

Для уточнения внутри API-контейнера с настоящей ролью `hmc_api` создан отдельный
Flask app и выполнены две последовательные серии по 19 запросов через test_client.
Это реальный route/retention/native worker/cache, без внешнего gunicorn/gateway
и без заголовка gateway request accounting. Concurrency здесь 1; на время
действует cProfile. Поэтому цифры не сравниваются напрямую с приёмочным cold.

[API-профиль](attempts/diag2/reports/diagnose-api.stdout.log) показал:

- 38 запросов → **76 новых DB-соединений** в основном API-процессе: по одному
  для удержания retention reader lock и для retention snapshot. В
  [domain.database](../../../../publication/domain.py) каждый вход открывает
  соединение и закрывает его после transaction. В
  [protect_reader](../../../../publication/api.py) обе операции выполняются до
  выдачи кешированного ответа.
- Подключения занимают 4389 мс из примерно 6883 мс измеренных запросов; вложенный
  профиль указывает на SCRAM `get_client_final → _make_salted_password → hi`.
  Эти времена получены **под cProfile**, который усиливает стоимость Python-loop.
- Reader-channel дополнительно выполняет 38 `native-resolve` (1557 мс) и
  38 `native-source` (196 мс). Первый включает независимую DB-транзакцию worker.
  `native-block` вызывается только 18 раз, `native-metadata` — один раз:
  во второй серии кеш результата работает, повторные resolve/source и
  retention-проверки сохраняются. Сам кеш не устраняет эти накладные расходы.

Субгипотеза о цене аутентификации проверена отдельной DB-only пробой:

```powershell
powershell -NoProfile -File docs/evidence/t23/diagnosis/auth-probe.ps1
```

[Измерение](attempts/auth1/reports/auth-profile.json), pg8000 1.31.5 / scramp 1.4.6:
20 настоящих последовательных подключений **без профилировщика** занимают
в среднем **23,45 мс** (21,72–33,13), с cProfile — 52,44 мс. В артефакте сохранены
исходный текст и SHA256 `scramp.utils.hi`: salted password вычисляется Python-циклом
HMAC/XOR. Отключение SCRAM или ослабление его параметров не требуется.

Итак, установлен существенный источник затрат: большое число свежих соединений
и повторная аутентификация при каждом запросе, в том числе до cache hit.
Подтверждены также последовательное накопление HTTP-задержек и отсутствие
повторной генерации на тёплой серии. Это **не полное разложение** всех 4359 мс:
gateway accounting, ожидание сериализованного reader-channel, транспорт и
другие DB-запросы отдельно ещё не профилированы. Причинный эффект конкретного
исправления не измерен; ускорение от увеличения concurrency не доказано.

Следующий различающий эксперимент — ограниченное переиспользование соединений
с обязательными transaction reset, deadlines, учётом разных DB-ролей и прежними
live access/retention проверками. Его нужно сравнить исходной HTTP-пробой,
а затем браузерным navigation-to-first-show и service regression gates.
Кешировать разрешения или пропускать retention ради скорости нельзя.

## Причина незакрытого вращения

В [исследовании первичных источников](../../../research/t23-orthographic-diagnosis.md)
разобраны pinned MapLibre 6.15.0, регистрация custom CRS, worker, смена проекции
и перспектива штатного globe. Текущий кандидат пересоздаёт карту только после
отпускания. Это реализованное ограничение, а не доказанная невозможность
непрерывной ортографии в выбранном движке. Нужен отдельный эксперимент с общим
динамическим центром для поля, подложки, отсечения, подписей, маркера и inverse
pick. Изменение одного shader uniform и прежний flat pan/zoom p95 недостаточны.

## Пробелы приёмки

Критерий 5 содержит реальный провал cold-бюджета и отсутствие p95 настоящего
вращения. Кроме того, физический Safari/iOS недоступен, установленный Google
Chrome desktop не проверен: Chromium Playwright обозначен дополнительной
пробой. Оценка managed arrays/textures не измеряет всю память браузера.
Это разные ограничения; непроверенный Safari нельзя объявлять неработающим.

Критерий 8 остаётся открыт из-за неполной матрицы и полной мобильной визуальной
приёмки: PNG Galaxy содержат canvas без HTML-контролов, подписей и маркера.
Это отсутствие свидетельств, не установленный дефект интерфейса. Архивирование
и успешная очистка прежних попыток сами по себе не закрывают оставшуюся часть.

## Решение после диагностики

Следующий шаг — измеренный эксперимент с уменьшением накладных расходов
сервисного пути при сохранении access/retention/deadline и ограничений кеша,
затем оригинальная navigation-to-first-show проверка. Сначала отдельная проба
непрерывной ортографии и реальный frame p95; после успешного кандидата —
полная матрица браузеров и UI, review, архив и retirement. Новый движок,
изменение научной модели, повышение request budgets и ослабление допусков
этим исследованием не предлагаются.

Исправление runtime не выполнялось; два красных диагностических условия
ожидаемо остаются красными. Критерии 1/5/8 не отмечены, №35 не закрыта.
Commit/push отложены по проектному правилу единого коммита после полной приёмки.

## Воспроизводимость и очистка

Диагностический runner — отдельный инструмент, runtime сервиса/рендерера в этой
работе не исправлялся. `tools/diagnose-t23-service.py` сохраняет профиль, а не
объявляет приёмку успешной; поле `within_3000ms=false` следует проверять отдельно.
В исходном browser runner тоже нет обязательного отказа по cold-budget:
`compatibility-probe-complete` не означает performance pass. Поэтому добавлен
отдельный красный проверяющий скрипт архивных timings.

В diag1 между start/end появился `tools/diagnose-t23-rotation.mjs`.
Runner вернул ошибку неизменности входов; это сохранённая диагностическая
попытка, не приёмка. Загружаемые API/renderer-исходники не менялись. В diag2
start=end и текущие байты всех 117 входов совпали; их копии сохранены в `inputs/`.

Все три новых проекта retired, архивы проверены по SHA256:
[diag1](attempts/diag1/retirement.json), [diag2](attempts/diag2/retirement.json),
[auth1](attempts/auth1/retirement.json). Независимый финальный inventory подтвердил
по каждому 0 containers, 0 networks, 0 volumes; `docker compose ls --all` пуст.
Новых браузеров, LAN listeners и сетевых правил эти пробы не создавали.
Старые девять проектов и их свидетельства не изменялись.
