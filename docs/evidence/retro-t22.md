# Ретроспектива реализации T22

Дата: 20.10.2026. Исходный коммит ретроспективы —
`fac79077353238a30562254e49ab4596b84d08db`.
Объект — завершённая [№34](https://github.com/stepanosokin/hmc-app-prototype/issues/34).
Источники: текущая сессия, [попытки и приёмка](t22/validation.md),
[итоговый review](t22/review.md), [согласование](t22/approval.md),
[архив](t22/artifact-index.json), [CI](../../.github/workflows/checks.yml),
[checker](../../tools/check_evidence.py) и [workflow](../development-workflow.md).

Изменения в порядке значимости:

1. **Архив T22 не охватывался существующим CI-checker.**
   В реализации вручную сверили 285 записей индекса, index и HEAD, но checker
   проверял только T3–T12. Добавлена ветка T22 в тот же инструмент и семь
   регрессий через его публичную точку входа. До исправления повреждённый
   синтетический снимок проходил; теперь отвергается. Проверяются длина,
   SHA256, Git object архивных файлов, уникальные относительные пути,
   успешность выбранного отчёта, очистка и связь записанных runtime-идентичностей.
   Внешние входы исторического индекса сверяются с записанными идентичностями
   отчёта, а не с будущими рабочими файлами. Тест подтверждает, что новая версия
   входа не обесценивает прошлую приёмку. Исторические T22-файлы не изменялись.
   В действующий CI job добавлен запуск негативных сценариев в том же образе.

2. **Повторный запуск мог перезаписать согласованные свидетельства.**
   Runner писал прямо в `docs/evidence/t22`; каждую итерацию приходилось сначала
   переносить вручную. По умолчанию он теперь пишет в игнорируемый
   `data/reports/t22`, с отдельным `T22_REPORT_DIRECTORY` для попытки. Изменён
   только путь вывода; полный прогон снова прошёл 160 проверок, архив принятого
   макета остался неизменным. Документированная команда соответствует инструменту.

3. **Прохождение browser assertions не устанавливает визуальную приёмку.**
   Review обнаружил начальный выбор старого расчёта после 47 успешных проверок.
   Позже 160 проверок прошли со слабо читаемым белым текстом на светлой подложке;
   исправление потребовало просмотра снимка. Пользователь также уточнял размеры,
   прозрачность, закрытие точки и обводку городов. Workflow ведёт к существующим
   инструкциям и требует сравнивать снимки на малом экране, в обоих шрифтах и
   подложках, отдельно проверяя исходную выборку. Визуальное решение остаётся
   за пользователем. Текущий макет уже согласован; его интерфейс не менялся.

4. **Сначала фактическое значение отказа, затем изменение драйвера.**
   Первые отказы шкалы K ошибочно связали с клавиатурным вводом: причиной было
   `253.14999999999998`, исправленное округлением. Следующий мобильный отказ
   действительно был связан с нажатием под прилипающей кнопкой; runner уже
   прокручивает цель в центр панели. Workflow связывает эти два случая с
   существующим runner, без нового общего линтера или дублирующего тестового слоя.
   Для вызова PowerShell-скрипта через `&` уточнена проверка `$?`: в сессии
   успешный documentation check ошибочно объявили неуспешным из-за старого
   `$LASTEXITCODE` от native-процесса.

5. **Согласование фиксирует входы и завершает визуальный этап.**
   После явного одобрения пересчитали hashes, обновили документы и сделали один
   коммит/push; исходные runtime-входы тогда не менялись. Workflow разделяет
   документальное завершение и изменения входов, требующие повторного браузерного
   прогона. AGENTS.md получил только триггер к этой ветке workflow; сторонние
   skills, глобальные инструкции и закрытая №34 не редактировались.

## Проверки этой ретроспективы

[Машинная запись](retro-t22-validation.json) фиксирует итоговые результаты.
В закреплённом `hmc-publication:checks` mypy прошёл по 53 исходным файлам,
семь тестов checker прошли, проверены 876 архивных ссылок. Новый runner прошёл
160 браузерных проверок, процессы и профиль удалены; результаты сохранены
отдельно от принятого архива. Проверяются также documentation links и Git diff.

Первая локальная попытка unittest столкнулась с доступом sandbox к TEMP;
известная папка попытки удалена, повтор вне sandbox воспроизвёл требуемый красный
тест повреждения архива. Первый контейнерный mypy обнаружил двойное имя модуля
`check_evidence`/`tools.check_evidence`. Тест перенесён рядом с инструментом и
импортирует его под тем же именем. В CI используется discovery `-s tools`;
сервисные images не требуют нового пакета или изменения Dockerfile.

Оба изолированных проекта проверок архивированы и retired существующим helper;
контейнеров, сетей и volumes после завершения нет. Первая неудачная попытка
сохранена, финальная прошла. Полные архивы находятся в
`data/archives/publication/hmc-publication-retro-t22-checks/` и
`data/archives/publication/hmc-publication-retro-t22-final/`.
Сервисный Compose-стенд, реальные GRIB/GPU/QGIS не запускались: изменения относятся
к инструментам проверки и workflow. Статус №34 и родительские задачи сохраняются.
