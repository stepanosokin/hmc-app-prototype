# Лимиты и учёт запросов T9

Срез [№21](https://github.com/stepanosokin/hmc-app-prototype/issues/21)
применяет одну политику перед всеми разрешёнными операциями gateway:
каталогом, состоянием задания, domain point, метаданными/байтами числовых
тайлов и scoped WMS. EDR position остаётся в сравнительном стенде T3;
publication stack пока не публикует EDR. Новых EDR-маршрутов этот срез не вводит.

Все ключи организации делят один бюджет. Демо имеет отдельный общий бюджет,
включая анонимный prefetch; заголовки клиента не задают организацию, часы,
request ID или результат кэша. Ротация ключа не сбрасывает бюджет организации.
Ошибочные неизвестные credentials не получают вымышленную организацию или
key ID. Отозванный ключ можно идентифицировать только по совпадению полного
секрета с сохранённым SHA256, никогда по открытой части ID.

Политика и журнал находятся в PostgreSQL, отдельно от метеоданных и кэша.
Миграция: `python -m publication.access migrate` от worker. При обновлении
старого volume сначала выполните существующий `publication/init-access.sh`
от администратора БД, затем миграцию. Повторная миграция сохраняет ключи,
политики и журнал. Gateway не владеет схемой и не может управлять ключами.

Оператор меняет настройки без перезапуска gateway:

```text
python -m publication.budgets configure --organization alpha --file /evidence/alpha-policy.json
python -m publication.budgets configure --public --file /evidence/demo-policy.json
python -m publication.budgets usage --organization alpha
python -m publication.budgets usage --public
python -m publication.budgets collect
python -m publication.budgets gis-limits
```

Команды запускаются от worker в изолированном Compose-проекте. Файл содержит
JSON с изменяемыми полями; отсутствующие поля берутся из прототипных defaults.
Это локальные защитные значения, а не обещание operational capacity или SLA.

| JSON-поле | Организация по умолчанию | Публичное демо по умолчанию | Допустимый диапазон |
| --- | --- | --- | --- |
| `requests` | 6000 попыток за скользящие 60 с | 3000 | 1–100000 |
| `bytes` | 512 MiB за скользящие 60 с | 512 MiB | 1024–1073741824 |
| `concurrency` | 4 | 2 | 1–4 |
| `seconds` | 30 с | 30 с | 1–30 |
| `output` | 4 MiB тела ответа | 4 MiB | 512–4194304 |
| `dimension` | 1024 px по каждой оси WMS | 1024 | 1–1024 |
| `zoom` | 0–6 | 0–6 | верхняя граница 0–6 |

`configure` заменяет политику, дополняя непереданные поля defaults организации;
при явной настройке public задайте его `requests`/`concurrency` отдельно, если
нужно сохранить исходные значения 3000/2. Все попытки организации в минутном
окне, включая отказы, занимают request budget. Байты — размер тела ответа,
без HTTP-заголовков и сетевых накладных расходов. На время активной работы
резервируется максимальный `output`; бюджет байтов может остановить запрос
даже при фактически небольших предыдущих ответах. Это консервативный допуск.

Gateway имеет 8 потоков, API — 4 одновременных обработчика. Генератор тайлов
один; занятый генератор возвращает 429 без очереди. Один f32-тайл содержит
332820 байтов, матрица фиксирована контрактом 0–6. Общий LRU числовых тайлов
и сырых метаданных ограничен `TILE_CACHE_BYTES` (по умолчанию 16 MiB,
разрешено 0–256 MiB). В T9 runner установлен бюджет двух числовых тайлов,
665640 байтов, чтобы доказать вытеснение на реальных запросах.

Gateway передаёт backend свой срок завершения, исключая клиентские заголовки.
Подпроцесс генерации принудительно завершается за оставшееся время,
максимум за 10 с; HTTP-чтение GeoServer ограничено 20 с и 4 MiB.
Ответ gateway ограничен `seconds`. При 504 слот concurrency консервативно
удерживается до 40 с от допуска: обрыв HTTP-клиента сам по себе не доказывает
остановку backend. Кроме того, API отмечает начало и окончание своей работы
в журнале. Начатая незавершённая работа продолжает занимать слот и после 40 с,
включая медленное холодное чтение; сборщик не удаляет такие записи.
Прямые backend-порты закрыты существующей internal-сетью.
Операторская команда `gis-limits` задаёт и считывает ограничения самого
GeoServer: `maxRenderingTime=20` секунд и `maxRequestMemory=16384` KiB.
Она также вызывается перед подготовкой каждого нового workspace; примените
её отдельно при обновлении уже опубликованного стека. Семантика параметров
описана в [официальном руководстве GeoServer](https://docs.geoserver.org/main/en/user/services/wms/configuration/).
Ограничение рендеринга не ограничивает сетевую запись ответа; её независимо
ограничивает HTTP-подпроцесс. Срок gateway передаётся также в PostgreSQL
socket/statement timeout API, включая ожидание reader-lock.
Контейнерные параметры этого стенда не устанавливают capacity SLA.

Повторная HTTP-попытка всегда создаёт новый request ID и отдельную запись,
включая cache hit, 400/401/403/404/405/429/503/504. Автоматических повторов
gateway нет. 429 содержит `Retry-After` и `Cache-Control: no-store`.
Успешная авторизация и допуск по квоте обязательны до обращения к API/кэшу.
Запрос, уже допущенный до отзыва, может завершиться; следующий проверяет ключ
заново. Тарифов, денежных единиц и платежей нет.

После аварии API или ошибки записи подтверждения завершения слот остаётся
консервативно занятым. Сначала остановите API и убедитесь, что его обработчики
больше не выполняются; затем от worker выполните
`python -m publication.budgets release --request-id <UUID>` и запустите API.
Команда разрешена только оператору. Она сохраняет исторические status/bytes,
отмечая прекращение backend-работы; это не успешная выдача и не автоматическое
предположение о завершении по одному таймеру.

Учёт содержит серверный request ID, UTC timestamp, bucket, организацию/key ID
при достоверной идентификации, тип операции, продукт/run/revision из проверенного
backend, HTTP status, duration_ms, число байтов тела ответа и cache outcome.
Для отказа до backend cache outcome равен `not-accessed`. Неизвестный cache
outcome остаётся `unavailable`; WMS не объявляется попаданием в кэш по одному ETag.
Секреты, URL query, пути к файлам и произвольные клиентские заголовки не сохраняются.

Журнал фиксирует начало допущенной работы до backend. Незавершённая после
аварии запись остаётся явно незавершённой, без вымышленного status/bytes.
Недоступное хранилище запрещает новые успешные выдачи; санитарная fallback-запись
пишется в stderr с признаком недоступного durable store. Она не означает
успешную запись в PostgreSQL. Оператор должен архивировать service logs при сбое.

Срок хранения usage задаётся отдельно от 7/30-дневного хранения прогнозов.
`python -m publication.budgets retention --days 30` задаёт 1–365 дней;
значение по умолчанию — 30. Запускайте `collect` регулярно от worker,
например ежедневным внешним расписанием; встроенного планировщика здесь нет.
Сборщик использует UTC БД; явный `--now` допускается только в изолированных
тестах и не меняет часы запросов/авторизации. Не удаляйте записи текущего окна
или активные reservations. Подробные значения и проверенные ограничения
фиксируются вместе с финальными доказательствами в `HMC_EVIDENCE_ROOT/t9`;
краткий результат хранится в `docs/validation/`.

Воспроизведение: `publication/run-budgets.ps1 -Project hmc-publication-t9-<новое-имя>`.
Runner проверяет SHA256 реального GRIB, фиксирует исходные входы, выполняет
T5/T8-регрессии и T9 HTTP-проверки, архивирует evidence и удаляет ресурсы проекта.
`-Development` предназначен для разработки и не заменяет финальный gate.
