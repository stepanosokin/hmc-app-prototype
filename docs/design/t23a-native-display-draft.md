## Решение, которое предлагается утвердить

Сначала проверить доставку нативных ячеек f32 с маской и halo, затем одну
билинейную интерполяцию в MapLibre custom layer. Кандидат имеет отдельное имя
`hmc-native-display/1`; он не заменяет `hmc-temperature-tile/2`. Приведённый ниже
профиль является конкретным проектом для эксперимента, а не опубликованным API.
Утверждение проекта разрешит его реализацию и сравнение, но не будет означать
прохождение научной или аппаратной приёмки. Если эксперимент потребует менять
существенные параметры, новый вариант надо представить на согласование.

## Сравнение вариантов до эксперимента

| Вариант | Интерполяция и ожидаемые ограничения | Текущее свидетельство |
| --- | --- | --- |
| Повторная интерполяция f32 v2 | Нативное поле → Mercator → экран; две интерполяции | Отклонённый способ T23: ошибка 2,558872628 K, предел 0,01 K |
| Нативные ячейки с halo | Нативные значения → одна GPU-интерполяция в экранной точке; независимая от режима доставка | Предлагаемый основной кандидат; точность GPU и преобразований ещё не измерена |
| Серверное поле в точной сетке экранных пикселей | Одна серверная интерполяция; клиент читает соответствующий пиксель без повторного bilinear | Кандидат сравнения; новая сетка и запросы при каждом изменении камеры, стоимость генерации и кеша ещё не измерена |

Серверные фиксированные ортографические/LAEA тайлы с обычным повторным bilinear
не дают сами по себе доказательства допуска. Для такого варианта потребуется
отдельное обоснование ошибки или сетка ровно в центрах экранных пикселей.
Сравнение серверного кандидата провести экспериментальным адаптером в изолированном
стенде через gateway; его публичный контракт не утверждается этим предложением.
Не объявлять кандидат проигравшим только из-за отсутствия реализации.

Результаты v2 сохранены в [записи T23](../validation/archives.md).
Сопоставление новых кандидатов должно использовать одинаковые экранные центры,
камеру и immutable selection, включая дробные позиции относительно нативной
сетки. Текущие архивы не доказывают точность новых вариантов.

## Предлагаемый профиль hmc-native-display/1

| Часть | Конкретное предложение |
| --- | --- |
| Metadata | `GET /api/v1/selections/{selection}/display/1/native.json` |
| Ячейки | `GET /api/v1/selections/{selection}/display/1/native/{column}/{row}.f32` |
| Защищённый профиль | Те же пути с `/org`; ключ передаётся существующим способом |
| CRS данных | `urn:hmc:crs:icon-sphere-6371229`, `+proj=longlat +R=6371229`, Greenwich, градусы, longitude/latitude |
| Matrix | `NativeCells256-{native_grid_sha256}`; один уровень, без zoom/overviews; шаг, размеры и bounds из проверенного manifest |
| Origin | Юго-западная внешняя граница первой ячейки; первая выборка находится на половине шага к востоку и северу |
| Orientation | Столбцы с запада на восток, строки с юга на север; это не ориентация v2 |
| Tile size / halo | 256×256 внутренних ячеек, по одной дополнительной ячейке с каждой стороны; всегда 258×258 |
| Адресация | `column,row` — целые неотрицательные индексы блоков; глобальный индекс выборки `(256*column+c-1, 256*row+r-1)` при `c,r=0..257` |
| Encoding | 258×258 little-endian float32 K, затем столько же uint8; row-major, столбец меняется быстрее строки; 0=missing, 1=valid; missing value=0; без сжатия, 332820 байт |
| Content-Type | `application/vnd.hmc.native-display-f32` |
| Краевые блоки | Сохраняют полный размер; индексы вне исходного массива имеют нулевое значение и маску 0; никаких новых нативных ячеек |
| Bounds | Полуоткрытый нативный footprint из manifest; геометрия покрытия строится из этих границ после той же datum operation |
| Selection | Исходная опубликованная selection и её полная identity; смена режима не создаёт новую publication revision |

Metadata возвращает версию и SHA256 утверждённого контракта, полный immutable
identity (`model,run,revision,field,level,valid_time,native_grid_sha256,member`),
matrix id, shape, spacing, origin, bounds, orientation, tile/halo/stored sizes,
диапазоны column/row, encoding, engine version, URL template, правила масок,
interpolation и координатную операцию. Параметры берутся из проверенного
manifest; этот профиль поддерживает только согласованную регулярную сетку T_G.
Не принимать от клиента произвольный CRS, путь к массиву, шаг или размер блока.
В блоке смещение значения равно `4*(r*258+c)`, смещение маски —
`4*258*258+r*258+c` байт. При маске 1 значение обязано быть конечным;
иные байты маски, NaN/Infinity или неверная длина означают повреждённый блок.

### Интерполяция и геометрия

В каждом центре экранного пикселя получить WGS84 lon/lat из обратной проекции.
Для EPSG:3576 использовать официальное определение WGS 84 / North Pole LAEA
Russia: lat_0=90, lon_0=90, x_0=y_0=0, WGS84, метры. Показ ограничить
геодезической широтой 45° с. ш.; сообщение: «Показано к северу от 45° с. ш.».
Для строгой ортографии использовать сферу отображения R=6378137 м,
WGS84 геодезические углы, явно заданные центр/масштаб и отсечение обратной
полусферы. Сфера отображения и сфера хранения имеют разные смыслы.

Из WGS84 lon/lat при **WGS84 h=0** перейти в геоцентрические Cartesian WGS84,
затем выполнить inverse Cartesian на сфере R=6371229 м без datum shift.
Нативная высота, получившаяся после перехода, не обнуляется перед обратной
операцией. Это продолжение ранее согласованной прототипной гипотезы v2,
а не новая гарантия геодезической точности или договорённость с производителем.
Перед реализацией сверить операции с действующими CRS в репозитории.

Для двумерной границы и координат нативных ячеек высота в manifest отсутствует.
Здесь обратная операция определена как пересечение геоцентрического луча
заданного native lon/lat с эллипсоидом WGS84 h=0, а не как Cartesian
преобразование точки на поверхности native sphere h=0. Для широт это
`phi_WGS84=atan2(sin(phi_native), (1-e²)*cos(phi_native))`, где
`e²=f*(2-f)`, `f=1/298.257223563`; долгота сохраняется. На полюсе широта
равна ±90°, долгота имеет условное значение и не меняет положение полюса.
Эту операцию применить к границе покрытия, контрольным центрам и независимому
эталону. Для реальных 3D координат с сохранённой высотой применяется обратный
3D pipeline; смешивать эти два случая нельзя.

Вне полуоткрытого нативного footprint значение missing. Внутри него дробные
индексы ограничиваются центрами крайних ячеек. Вычислить bilinear по четырём
нативным значениям; missing у любого участника с положительным весом даёт
missing, веса не перенормируются. Нулевой вес не распространяет missing.
Использовать `texelFetch` и явные веса; не включать аппаратный LINEAR для
числовой текстуры и не интерполировать заново готовое отображаемое поле.
Halo соседних блоков обязан совпадать с соответствующими исходными ячейками.

Подложка, подписи, граница покрытия, поле и маркер проходят одну геометрию
отображения и одинаковое отсечение. Обратный выбор возвращает WGS84 позицию,
а point API продолжает выбирать nearest-native-cell. Внешний WMS/QGIS,
point/EDR, GRIB/Zarr/COG и frozen v2 не получают нового контракта.
Отображение не получает raster через массовые вызовы point/EDR: оно загружает
только ограниченный набор display-блоков. Клик вызывает существующий
point/EDR sampler и не запускает загрузку всего растра или display-блоков;
это отдельно проверить наблюдением сетевых запросов при повторных кликах.

### Ресурсы, кеш и готовность

Для реального образца 1377×657: 18 блоков (6×3),
`18*258*258*5 = 5990760` байт ≈5,713 МиБ на весь слой с halo и padding.
Без блочного padding исходные значения с маской занимают 4523445 байт
≈4,314 МиБ. Это расчёты структуры, не измерения HTTP, GPU или первого показа.
Metadata и повторные запросы тоже учитывать в лимите 8 МиБ на вид; не загружать
одни блоки повторно при смене проекции в пределах той же selection.

Предлагаемый клиентский лимит: одна активная selection, до 18 блоков для
этого профиля, не более двух одновременных запросов; отмена устаревших загрузок.
Учитывать одновременно fetch-буферы, decoded arrays, upload-копии, числовые
текстуры и framebuffer; общий предел 128 МиБ. Полноэкранный framebuffer при
высоком DPR может доминировать; предельные viewport/DPR должны входить в пробы.
Нельзя принимать оценку одного набора текстур за измерение памяти всего вида.
Цели p95/первого показа остаются теми, что указаны в №37.

Серверный кеш: до 16 МиБ на процесс совместно для metadata и блоков нового
профиля, LRU, один генератор на процесс, hard timeout не более 10 с и остатка
request deadline. Существующие request/output/concurrency budgets gateway не
повышаются: один блок меньше текущего предела ответа 4 МиБ. Ключ содержит
contract version/hash, matrix id, CRS/operation, grid shape/spacing/origin/bounds,
encoding, engine version, полную immutable identity, selection и column/row.
Client GPU cache также включает режим, параметры display CRS и engine;
исходные блоки могут переиспользоваться между режимами по их неизменной identity.

До cache hit/miss проверять access, eligibility и retention. Проверять
целостность опубликованного хранилища, в том числе исчезновение array/chunk
после прогрева; не превращать fill values в опубликованные числа.
Перед дорогой работой проверить выходные размеры и срок запроса. Отмена клиента
не означает завершения backend: существующий учёт должен удерживать слот до
реальной остановки, expired queued work не должно запускаться позже.
При output rejection сохранить известные product/run/revision/cache metadata.

Representative readiness: для каждого поля/срока проверить metadata и блоки
(0,0), (1,0), (2,1), (5,2), детерминизм байтов, маски и общую halo пары первых
блоков. Готовность нового профиля не подразумевается старым `tiles.json`;
предусмотреть отдельный результат probes до объявления нового профиля готовым.
Остальные блоки генерируются ограниченно, полного глобального prebuild нет.

## Проверки после утверждения

Пользователь 20 октября 2026 года подтвердил две публичные границы TDD:
metadata/блоки через gateway и MapLibre renderer. До написания тестов открыть
один вертикальный срез с failing test, затем минимальную реализацию.

1. Через gateway сравнить f32/masks с независимо декодированным исходным GRIB
   и одинаковые экранные точки двух кандидатов с независимым scalar bilinear.
   Разделить ошибку кодирования ≤0,001 K, координат/GPU и суммарную ≤0,01 K;
   COG ≤0,0001 K проверяется отдельно и не суммируется как разрешение на ошибку.
2. Проверить весь набор блоков, seams/halo, missing с нулевыми/положительными
   весами, partial tiles и полуоткрытые края. Полюс, ±180°, горизонт и отсечение
   воспроизводить явно синтетическими полями; не выдавать их за ICON-EU coverage.
3. Снять реальный GPU readback в тех же экранных центрах. Проверить highp
   координатную арифметику, особенно у горизонта, границы и при большом zoom;
   при необходимости локальные индексы/компенсированную арифметику проверять
   экспериментом. Доставка f32 сама по себе не доказывает GPU допуск.
4. Через защищённый/public gateway проверить warm-cache revocation/rotation,
   retention, storage loss/recovery, timeout, queued cancellation, concurrency,
   output limit, лимиты количества блоков/bytes, metadata и usage accounting.
   Смена режима сохраняет selection; point/EDR возвращают прежний смысл.
5. На frozen inputs выполнить полный unittest discovery и mypy; для изменений
   API/gateway/cache/readiness потребуются реальный T5, T6 и T8/T9 регрессии.
   Предпочесть комбинированный T12 gate, включающий T5/T9/полный T8/T11 и suite,
   плюс T6 для нового кеша. T10 numerical/fault checks обязательны.
   T7 добавляется при изменении retention или миграции retained revisions;
   новый путь отдельно проверяет expiry после прогрева и рестарта даже без
   изменения retention. Если T12 выполняется как официальный integrated gate,
   его desktop-фазы не опускать; новые обещания desktop CRS не добавляются.
6. Архивировать hashes/версии/камеры/входы, исходный commit, Git-filter byte
   identity, failed attempts и review. После каждого стенда выполнить retirement
   и проверить нулевые ресурсы. Реальные Android/iOS и аппаратные frame/memory
   gates вести отдельно; desktop viewport emulation не заменяет их.

## Состояние этой подготовки

Критерии №37 остаются неотмеченными до выполнения соответствующих проверок.
Проект согласован; результаты реализации и эксперимента фиксируются отдельно.
Явное согласование предусмотрено требованием №37 и разделом
[Scientific contracts and evidence](../development-workflow.md#scientific-contracts-and-evidence).
До завершения всей задачи единый ticket commit/push не выполняется.

Проверки подготовки: ссылки документа прошли `tools/check-documentation.ps1`,
SHA256 частного образца совпал с `SAMPLE_SHA256`; арифметика размеров проверена
отдельно в PowerShell. Проверены отсутствие хвостовых пробелов и final newline.
Попытка трактовать код 1 `git diff --no-index --check` для нового файла как
ошибку whitespace заменена прямой проверкой текста; это не отказ сервиса.
Два независимых review по навыку `code-review`: Standards — нарушений не найдено;
Spec — уточнены обратная 2D datum operation, бинарные offsets/finite values
и отсутствие raster-loader при кликах. Это review предложения, не реализации.
Браузерные/Compose тесты не запускались, новых тестовых ресурсов не создавалось;
read-only Docker inventory не содержал проектов hmc. Полная runtime-приёмка,
архивы её попыток и retirement относятся к последующей реализации.
