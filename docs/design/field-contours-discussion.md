# Изолинии полей: согласование оформления

Состояние на 29.10.2026: требования согласованы; пользователь поручил создать
тикет и приступить к реализации. Исторические примеры сохранены отдельно.
Задача: [№74](https://github.com/stepanosokin/hmc-app-prototype/issues/74).
Архитектурное решение: [ADR 0011](../adr/0011-native-browser-contours.md).

## Подтверждено пользователем

- Давление в интерфейсе приложения отображается в гПа: легенда, точка,
  графики и подписи. Исходные данные, API и GIS сохраняют свои единицы.
- Изолинии накладываются на цветную заливку всех фоновых растровых полей.
  В тёмной теме линии чёрные, в светлой серые (замена белых подтверждена
  29.10.2026 после первого просмотра).
- Линия разрывается под числовой подписью. Верх подписи направлен в сторону
  увеличения показателя, в том числе если число перевёрнуто для читателя.
- Не более семи подписей суммарно на видимую карту. Ориентир — около пяти;
  при недостатке места или линий допустимо меньше.
- Шаг целый в отображаемых единицах. Для интерфейса согласованы г/кг для
  удельной влажности, мм/ч для интенсивности осадков, см для высоты снега.
  Это пересматривает прежнее решение [ADR 0009](../adr/0009-field-value-validity.md)
  о сохранении кг/кг именно в отображении; численные исходники не меняются.
- Для сравнения используются охваты: вся область прогноза, несколько регионов,
  один регион. Варианты шага одного поля сравниваются на одинаковых данных.
- Шаг указан в легенде, например «Изобары проведены через 50 гПа».
- Общий переключатель «Изолинии» скрывает линии вместе с подписями, сохраняя
  заливку. При открытии страницы включён; выбор между сеансами не сохраняется.
- Примеры передаются картинками в чат; отдельные страницы эскизов не создаются.
- После просмотра пользователь подтвердил скрытие коротких контуров,
  упрощение в пределах одного экранного пикселя и сглаживание изолиний.
  Пользователь утвердил суммарный предел отклонения упрощённой и сглаженной
  линии в один экранный пиксель от исходной, порог длины 60 экранных пикселей
  и оттенок серого `#707070`. Исходное численное поле не сглаживается.
- Построение изолиний в приложении — на лету в браузере, в фоновом потоке,
  с кешированием линий. Изменения темы меняют оформление; навигация требует
  перепроецирования, экранной детализации и размещения подписей, а при новом
  шаге недостающие уровни строятся по необходимости. Скорость и расход памяти
  должны быть проверены на реальных полях. Предрасчёт текущих PNG отдельным
  скриптом служит только сравнению оформления, не реализует этот путь.
- Классы масштаба определяются шириной видимой карты в километрах:
  мелкий — более 6000 км, средний — более 2000 и не более 6000 км,
  крупный — не более 2000 км. Поведение охвата проверяется во всех проекциях;
  одинаковые значения zoom не используются как универсальные границы.
- Для четырёх диагностических полей пользователь утвердил выбранные шаги
  именно исходных чисел. В легенде явно отмечаются неопределённые или
  противоречивые единицы. Дождь не переводится автоматически в мм/ч до
  установления физического смысла. Это временное правило не подтверждает
  корректность метаданных.

## Следующая развилка

Конкретные шаги, границы масштабов, численные параметры оформления, временное
правило диагностических полей и численный контракт нативной сетки подтверждены
пользователем. Переход к реализации явно разрешён. Конкретный алгоритм выбирается
по технической проверке; повторное разрешение на согласованный объём не требуется.

Выбор передаётся тройкой «мелкий / средний / крупный», например
«давление на уровне моря: 10 / 5 / 2 гПа»; это B1/B2/B3 соответствующего
листа. Допускаются разные ряды в одной тройке. Можно принять предлагаемую
таблицу целиком и перечислить только исключения.
Пользователь также может задать собственный положительный целый шаг для
каждого показателя и масштаба: показанные варианты не ограничивают выбор.
Достаточно указать тройку шагов либо изменить только один масштаб.
Пользователь уточнил: собственные значения вводятся сейчас в чате для
настройки оформления. Ручной ввод шага в самом приложении этим требованием
не запрошен.

## Уточнение численного контракта

Пользователь спросил, будут ли изолинии строиться по сетке Zarr без учёта
рендеринга растра, и подтвердил предложенный ниже контракт ответом «да»:

- Источник геометрии — значения и числовая маска NoData нативной сетки Zarr.
  Отрисованное цветное изображение, его палитра и прозрачность не являются
  входами расчёта изолиний. Интерполяция, используемая только для растрового
  отображения, также не подменяет нативную сетку.
- Браузер получает численные данные через сервис, а не читает Zarr напрямую.
  Существующие тайлы отображения пригодны только если сохраняют необходимые
  нативные значения и маску; иначе потребуется отдельная передача этих данных.
  При реализации подтверждено: `native-display/3` передаёт нативные ячейки
  float32 с объявленным допуском и числовой маской, без экранной выборки.
  Новый серверный продукт для построения изолиний не требуется.
- Построение нативной геометрии выполняется в фоновом потоке; проекция,
  фильтрация по экранной длине, ограниченное упрощение/сглаживание и подписи
  относятся к экранному представлению. Исходные значения не изменяются.
- PNG-примеры построены после выборки на вспомогательную сетку отображения.
  Они служат сравнению оформления и не доказывают нативный численный контракт
  будущего браузерного построения. Его потребуется проверить отдельно.

## Инструменты текущих примеров

Python-генератор читает локальные GRIB через GDAL; NumPy и SciPy используются
для численных массивов и выборки на вспомогательную сетку отображения,
pyproj — для преобразования координат. Геометрию изолиний строит
`matplotlib.contour`, подписи с разрывом размещает `clabel`; направление
верха текста задаётся по локальному градиенту. Shapely упрощает линии и
проверяет двустороннее включение в буферы шириной один пиксель; локальное
скругление углов выполняет код генератора с квадратичными кривыми Безье.

Это воспроизводимые графические примеры, а не изображения, созданные
генеративной моделью, и не реализация браузерного пути. На этапе этих примеров
браузерный алгоритм ещё не был выбран; принятое решение описано ниже.

## Обнаруженные ограничения источника

Для локального `igfi03000000s.ENA6km.grb` ecCodes подтверждает накопление
за 0–72 ч у осадков, снегопада и снежной крупы; их количество сохраняется
в кг/м². GDAL ошибочно предлагает для части этих продуктов обобщённую
подпись интенсивности: её нельзя использовать для выбора единиц.

Поля `lsrr`/`crr` содержат сочетание единиц кг/(м²·с) и статистического
процесса накопления. Пока физический смысл не установлен, их нельзя
молча пересчитывать в мм/ч или объявлять количеством осадков.
Поля GRIB 0/6/1 и 0/0/18 имеют `units=unknown` по ecCodes;
подписи GDAL сами по себе не устраняют эту неопределённость.

Сравнения генерирует [preview-field-contours.py](../../tools/preview-field-contours.py).
Это иллюстрации для выбора оформления, а не приёмка браузерного рендерера
или независимая научная проверка декодера. Полные картинки и записи генерации
хранятся по правилам [внешнего архива](../validation/evidence-storage.md).

## Реализация браузерного пути

Выбран собственный marching squares с асимптотическим решением неоднозначных
ячеек и сшивкой линий через halo блоков. Worker получает копию одного нативного
блока за раз; исходные массивы остаются у растрового слоя. Невалидная числовая
маска исключает ячейку; нулевое значение остаётся числом независимо от прозрачности
заливки. Завершённые компоненты освобождаются по мере обхода блоков.

Линии проецируются локальным proj4js, обрезаются по видимой области, упрощаются
с допуском 0,3 CSS-пикселя и скругляются в пределах 0,6 пикселя. Квантование
экранных координат допускает дополнительно не более 0,09 пикселя; суммарный
предел остаётся меньше одного пикселя. Подписи и разрывы рисует Canvas 2D.
Новые сетевые зависимости не добавляются.

Ширина карты — сумма сферических дуг вдоль горизонтальной середины видимой
области; учитывается только определённая часть выбранной проекции. Это даёт
единый смысл километров при смене проекций. При увеличении worker обходит
проекции всех нативных ячеек и рассчитывает окно с запасом 64 ячейки,
сохраняя только две строки координат. Разреженная обратная выборка
не ограничивает это окно; полный охват сохраняется без обрезки. Проверка
прямым PROJ-преобразованием всех узлов проверяет отсутствие видимых пропусков.
Кеш экранной геометрии ограничен 4 MiB, общий управляемый бюджет приложения —
128 MiB. При нехватке места кеш освобождается до запуска нового построения.
Уровни обрабатываются группами не более восьми для ограничения рабочего графа;
набор уровней и выбранный шаг сохраняются. Экранные координаты обычно хранятся
как пары uint16 с контролируемым шагом квантования; для очень широкого окна
используется float32. Управляемые буферы и оценка рабочего графа учитываются
отдельно от измеряемой кучи JavaScript и памяти процесса браузера.
