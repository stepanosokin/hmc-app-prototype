# WMS: серверный вариант против фрагментов и мигания QGIS

Продолжение [диагностики масштаба](qgis-wms-scale-diagnosis-20261112.md).
Исходный commit: `c87c2e3019a31ded8b74c6c332b7184287cce82f`.
Объём: согласованная базовая локальная диагностика, Windows/PowerShell,
QGIS 3.44.11 через MCP и существующий `hmc-app-live`. Требование пользователя:
обычное WMS-подключение без изменения настроек QGIS. Изменения приложения
и внедрение решения в этот этап не входят.

## Причина и уточнение предыдущего вывода

Малый предел GetMap является серверным триггером клиентского дефекта.
[MAX_MAP_SIZE](../../publication/wms.py) равен 512; scoped capabilities
объявляют его через MaxWidth/MaxHeight. QGIS использует предел для блоков
основного raster iterator, а промежуточный renderer создаёт другой iterator
с умолчанием 2000. При перепроекции эти разбиения приводят к разным запросам
источника/разрешениям и несовпадающему наполнению кеша. Промежуточная отрисовка
может получить прозрачные участки и заменить ими уже нарисованные данные.
Последний основной блок не восстанавливает всё ранее затёртое изображение.

Это объясняет зависимость от масштаба, CRS и размера окна: меняется разбиение
растрового конвейера и запросов исходной проекции. HTTP 200 и отсутствие
ошибок renderer не гарантируют полноту итогового canvas. Одноцветный источник
воспроизводит тот же дефект без GRIB, GeoServer, сети приложения и admission.

Причинная связь подтверждена изменением серверного контракта при включённом
RenderPartialOutput. Детальная цепочка согласуется с исходниками QGIS;
исправленная C++-сборка с инструментированием не проверялась:

- [Основной renderer и preview](https://github.com/qgis/QGIS/blob/final-3_44_11/src/core/raster/qgsrasterlayerrenderer.cpp):
  `render()` задаёт размеры provider, `onNewData()` оставляет defaults.
- [WMS provider](https://github.com/qgis/QGIS/blob/final-3_44_11/src/providers/wms/qgswmsprovider.cpp):
  `maximumTileSize()` читает capabilities; `draw()` строит блоки, preview
  использует доступные кешированные изображения и не загружает недостающие
  блоки в tiled-ветке.
- [RasterDrawer](https://github.com/qgis/QGIS/blob/final-3_44_11/src/core/raster/qgsrasterdrawer.cpp):
  `CompositionMode_Source` заменяет изображение вместе с прозрачными пикселями.

Предыдущая рекомендация только клиентского исправления была слишком узкой.
Повышение concurrency/таймаутов не устраняет эту причину. Но увеличение
допустимого размера GetMap до 2000 — проверенный кандидат серверной
совместимости, а не просто неподтверждённое предположение о лимитах.
2048 и 4096 также прошли минимальный пример; универсальная необходимость
строго точного значения 2000 из этого не следует. Предлагается меньший
проверенный размер, совпадающий с default iterator данного QGIS.

## Проверки

Во всех строках ниже, кроме явно обозначенного контроля, RenderPartialOutput
включён. Свежий loopback URL на попытку исключает маскировку прогретым кешем.
Собственные скрытые QgsMapCanvas не добавляют слои в проект пользователя.

| Сценарий | Результат |
| --- | --- |
| Живой исходный WMS, 2t, LAEA 60°/90°, 1206×521, 1:17 855 000, предел 512 | 1,7%, повторные падения заполнения до 0%; 33 ответа 200; 12,3 с |
| Тот же вид, посредник с пределом 2000 | 100%, без регрессии заполнения; 5 ответов 200 |
| Точный пользовательский слой t, source EPSG:3857, LAEA 60°/90°, 1206×521, 1:75 364 600, предел 2000 | 100%, без мигания; 7 ответов 200 |
| Одноцветный WMS, source EPSG:4326 → LAEA, 2400×1000, 1:5 млн, предел 512 | 7,1%, мигание; все 94 ответа 200 |
| То же, предел 1024 | 14,7%, мигание; все 29 ответов 200 |
| То же, предел 2000 / 2048 / 4096 | 100%, без мигания во всех трёх случаях |
| То же, предел 512, RenderPartialOutput выключен | 100% |
| Одноцветный WMS, EPSG:3857 → EPSG:3857, предел 512 | 100% при включённом промежуточном выводе |
| Повтор реальных PNG, 2t, LAEA, 2400×1000, 1:5 млн, предел 2000 | 100% с обоими значениями RenderPartialOutput; 22/17 ответов 200; 4,7/2,3 с |

Точный пользовательский слой: GRIB-4-1, run `2026-10-21T06:00:00Z`, revision
`305358c4c181b6f67e9ee23f64e28ea6d9d44a6cc2876aa4827741d5f9922f28`, field
`3d691f71cdaaf46559eb578287a069b847d84ba6983c314b0cd6eafbfd4eeb9d`, default TIME
`2026-10-24T06:00:00Z`, origin `http://localhost:8140`.

Посредник собирал крупный PNG из обычных GetMap не более 512×512 с сохранением
CRS, BBOX и размера пикселя. Это эксперимент совместимости; такой сборщик
не предлагается добавлять в продукт. Он не доказывает производительность,
попиксельную эквивалентность одного крупного GetMap или достаточность бюджетов.
В широком живом опыте сборка увеличила число запросов, возникли 8 ответов 429;
эта попытка не использована для причинного сравнения. Сохранённые успешные PNG
переиграны локально с задержкой 0,3 с, без обращений к приложению: полный кадр
и отсутствие мигания подтверждены отдельно.

Есть существенная незакрытая граница: 2t, source EPSG:4326, LAEA, 2400×1000,
1:17 855 000, предел 2000 дают 90,75% относительно географической контрольной
маски. Это одинаково с обоими значениями RenderPartialOutput, без мигания,
в живом опыте и при повторе PNG. Одноцветный источник на том же виде даёт
100%. Причина этой потери покрытия в данном исследовании не установлена;
она должна быть объяснена до заявления о полной совместимости всех видов.

## Предложение решения

1. Поддержать обычные scoped WMS GetMap до 2000×2000 в GeoServer-пути приложения.
   Согласовать `MAX_MAP_SIZE`, проверку gateway, API, forwarded dimension
   и объявленные MaxWidth/MaxHeight. Не объявлять размер, который endpoint
   затем отклоняет. Текущие Limits.dimension default/max равны 1024;
   необходимо явно обработать существующие public/org политики, а не поменять
   только константу. Незаметное возвращение к пределам 512/1024 возвращает триггер.
2. Сохранить ограничение одновременно работающих GetMap и общий deadline.
   Измерить память/время и максимальный размер PNG на реальном GeoServer:
   2000² RGBA — около 16 МБ только на один несжатый буфер; текущий output
   ограничен 4 МиБ. Проверить необходимость изменения output/reservation,
   не повышать остальные бюджеты автоматически и не вводить сборку плиток.
3. Приёмку выполнять реальным canvas со стандартным RenderPartialOutput,
   свежими подключениями, холодным/тёплым кешем, несколькими масштабами,
   размерами окна меньше/больше 2000, CRS 4326/3857 → LAEA/3576/3857,
   минимум двумя сроками, Identify и проверкой отсутствия потери заполнения
   между кадрами. Сравнить географически правильные маски и численные значения.
   Включить точный пользовательский случай и незакрытый случай 90,75%.
   После реализации нужны полные применимые T9/T11 и проверка ресурсоёмкости.
4. Для долгосрочного устранения дефекта QGIS предложить одинаковое разбиение
   основного/preview конвейера и исключение затирания завершённых областей
   неполным preview. Это направление C++-исправления требует собственной
   регрессии и проверки; существующая версия с готовым исправлением не установлена.

Рекомендуемый первый шаг — серверная совместимость с размером 2000 и описанной
приёмкой. Это не требует настройки пользователей и укладывается в существующий
WMS-путь. Внедрение до проверки дополнительного пробела покрытия и ресурсных
границ не предлагается. Диагностика и предложение завершены; продуктовый фикс
не реализован, новая issue не создавалась, состояние прежней issue не менялось.

## Воспроизведение и доказательства

Исходный красный вызов внутри QGIS: `runpy.run_path('tools/diagnose-qgis-scale.py')`
с абсолютным путём, затем `probe_scale(baseline_config)`. Получено
`Fragmentary WMS: 1.7%; HTTP {'200': 33}`.
Архив содержит `probe-server-contract.py`, конфиги, snapshots программы,
PNG ответов/кадров, upstream-запросы, результаты и cleanup каждой попытки.
`run(config)` поддерживает live assembly, replay и явно синтетический источник.
Эти диагностические режимы не являются реализацией сервера.

Первый опыт переписал namespace XML через ElementTree, и QGIS не принял слой:
эта ошибка посредника устранена заменой только значений MaxWidth/MaxHeight.
Первый replay baseline не имел сохранённых PNG из-за регистра Content-Type
в старой программе и исключён. Контроль reference PNG и полноценные сохранённые
крупные ответы использованы в успешных replay. Все неудачные попытки сохранены.

Все собственные proxy закрыты, потоки остановлены, созданные canvas удалены;
проверки project_unchanged истинны. Docker-ресурсы не создавались, hmc-app-live
сохранён. Производственные настройки и исходники не менялись.
Историческая проверка всего архива не запускалась.

Архив: `qgis-wms-server-compatibility/20261112-diagnosis` относительно
HMC_EVIDENCE_ROOT, 440 файлов; SHA256 `archive-index.json`:
`7ee86f4b6ba049b3b7f71ef415cc575938be901fa18fdec3071411009920f79d`.
Все 19 попыток имеют подтверждённую очистку, включая две ошибки подготовки
посредника/replay. Ссылки двух изменённых документов проверены. Финальная
проверка Docker подтверждает пять работающих служб hmc-app-live;
доступ к Docker API потребовал повторного read-only вызова вне sandbox.
