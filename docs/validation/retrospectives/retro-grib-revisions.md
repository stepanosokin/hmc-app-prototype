# Ретроспектива управления редакциями — №71

Разобрана текущая сессия реализации [№70](https://github.com/stepanosokin/hmc-app-prototype/issues/70),
завершённая commit `a8e6221ece1fda6670540a490fa7ccbcf85d1457`.
Первичные журналы и их архивные SHA256 связаны в
[записи приёмки](../grib-revisions-70.md). Изменения этой ретроспективы —
проверки и инструкции агента; приложение, GRIB, правила хранения и live сохраняются.

1. **Высокий приоритет — проверка одного теста скрыла взаимодействие сценариев.**
   Development запускал только one-off cleanup. В полном T7 следующий тест
   получил `StopIteration` (116,423 с): повторная отправка вернула завершённое
   задание со снятой редакцией. После разделения delivery identities следующий
   прогон (138,358 с) собрал файлы прошлого сценария и нарушил ожидание нового
   grace. Промышленный загрузчик работал штатно; исправления fixture вошли в №70.
   Теперь Development запускает one-off и обычный lifecycle последовательно.
   [AST guard](../../../tools/check-retention-preflight.ps1) проверяет вызов
   до Docker, discovery и оба существующих селектора. Его отрицательные случаи
   выполняются в существующем Windows scope и manual CI.

2. **Средний приоритет — слишком глубокий путь остановил cleanup после успеха.**
   `development-c.stderr.log` содержит Copy-Item DirectoryNotFoundException
   на пути с повторными project/UUID. Успешный тест сам по себе не позволял
   удалить стенд. №70 уже вынес операции из T7-дерева; общий retirement helper
   менять не требуется. В [cleanup](../../development/cleanup.md) добавлен
   условный указатель на рабочий layout и порядок сохранения неудачной копии.

3. **Средний приоритет — подготовка доказательств повторяла ручную работу.**
   Backend inventory не включает корневой CLI и `.mjs`; №70 дополнил его
   CLI inventory и полным снимком. [Service review](../../development/services.md)
   теперь указывает этот разрыв до новой CLI-проверки. Существующие архиватор,
   snapshot compare и проверки hash уже достаточны; новый архиватор не добавлен.

4. **Низкий приоритет — проверочные запросы и обёртки давали лишние сбои.**
   Развёрнутый каталог вернулся из API за 33,468 с и превысил 30-секундный
   deadline gateway; компактный каталог прошёл. Отдельная обёртка считала
   пустой LASTEXITCODE ошибкой после успешного PowerShell-скрипта.
   В service docs добавлены условия выбора компактного представления и
   существующего checked launcher. Продуктовые таймауты не меняются.

Ранние mypy-ошибки уже ловились существующей проверкой типов; она не дублируется.
Правило freeze уже есть в workflow: редактирование входов во время приёмки
привело к повторным фазам, но новой копии этого правила в AGENTS.md нет.
Сторонние skills и глобальные инструкции не изменяются. Ретроспектива не
утверждает дефект сборщика на основании загрязнённого тестового состояния.

## Проверка изменений среды

- Полный Windows scope прошёл: синтаксис 38 PowerShell-файлов, process exits
  0/7, документация, fixture/preflight и Node-проверки. Guard текущего T7 и
  11 отрицательных случаев прошли без Docker и без исполнения runner.
- На отдельном `hmc-publication-t7-retro71` изменённый Development выбрал
  ровно два сценария в нужном порядке: оба прошли, 133,591 с, native exit 0.
  Они используют настоящий ICON-образец с SHA256
  `dddfd6c63ba73e5e7337c21e105f16417003429f8179a44ca58bb110cb43736a`.
- Заморожены 264 входа. Сравнение до/после прошло; полный режим T7 вне
  Development и ресурсно свободного guard совпадает с исходным commit.
  Приложение и полный gate не менялись; T5, полный T7, браузер и историческая
  проверка архивов повторно не запускались. Приёмка №70 сохраняет прежние байты.
- Архивирование проверяет размеры и SHA256. Один T7-проект удалён:
  контейнеров/сетей/томов осталось ноль. Собственный process-fixture скопирован,
  проверен и удалён из Temp. Отрицательные fixtures очищены своими проверками.
  Пять служб `hmc-app-live`, исходники и общие кеши сохранены; live-команды не
  применялись. Проверки документации/AST не создавали сервисных ресурсов.
