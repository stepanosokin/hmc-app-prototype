# Ретроспектива многослойного WMS — №109

16.11.2026. Основание — текущая сессия, [результат №109](../wms-109.md),
[индекс первичных материалов](../wms-109.archives.json) и
[коммит 6e71c20](https://github.com/stepanosokin/hmc-app-prototype/commit/6e71c2054bc15c365f1f8ee9860373d717177988).
Пути журналов ниже заданы относительно `HMC_EVIDENCE_ROOT/wms109/`.
Согласованы минимальные проверки, локальные Windows PowerShell + Node/Python,
без запуска Docker/QGIS/live. Ретроспектива не переоткрывает реализацию №109.

1. **Высокий приоритет — дорогой gate раньше проверки desktop-плана.**
   Первый полный HTTP Prepare прошёл, затем расширение viewport потребовало
   нового полного прогона. В
   `http-and-expanded-desktop-development-20261116/large-identify-development2.json`
   реальный GetFeatureInfo передал WIDTH=638, HEIGHT=478, I=1599, J=900:
   внешний canvas был увеличен, а ни разу не показанный Qt viewport остался
   прежним. Исправление фактического layout и его assertions вошло в №109;
   приёмка завершена только на новых неизменных входах final2.

   Добавлен [source preflight](../../../tools/check-qgis-preflight.mjs):
   он сравнивает renderer/Identify с текущим MAX_MAP_SIZE и требует инициализацию
   layout и assertions фактических размеров до Identify. Проверка не импортирует
   QGIS, не создаёт сервисы и не доказывает поведение Qt. Неизвестный после
   рефакторинга исходный план отклоняется с просьбой его пересмотреть.
   [Регрессии](../../../tools/test-qgis-preflight.mjs) воспроизводят малые
   размеры, дрейф лимита, отсутствующие/поздние viewport-проверки и код возврата
   CLI. Guard и его регрессии подключены к существующим Windows/All и Windows job
   manual CI. [QGIS guidance](../../development/qgis.md) направляет к нему перед
   выделением T11-стенда и к реальному pinned-client Development до freeze.

2. **Высокий приоритет — асинхронное Add приняли за завершённое действие.**
   В финальном desktop-проходе проверка `len(added) == 4` сработала до окончания
   callback; последующий readback подтвердил четыре загруженных слоя.
   На тех же входах повторное наблюдение прошло. Это зафиксировано в
   `orchestration-and-frozen-inputs-20261116/acceptance-result.json` и в отфильтрованной
   выборке текущего root-session до команды retro.

   [QGIS guidance](../../development/qgis.md) теперь различает queued action
   и наблюдаемую готовность owned layers/providers в следующем MCP-вызове.
   Частичная фаза не должна давать passed: reviewer нашёл этот риск,
   а `completed_phases` и публикация наблюдений только после последней легенды
   уже исправлены в №109. Новое правило общего CODING_STANDARDS не требуется:
   готовность зависит от клиентского состояния, а reviewer сработал.

3. **Средний приоритет — адрес MCP и PID launcher не совпадали с реальностью.**
   Открытый QGIS отвечал на 9877, инструменты ожидали 9876. Связь восстановлена
   временным локальным forward без изменения пользовательской конфигурации.
   При cleanup процесс 31984 оказался Node shim; фактическим слушателем был
   его дочерний 11360. Остановка только launcher оставила порт открытым.
   `orchestration-and-frozen-inputs-20261116/mcp-forward-cleanup.json`
   подтверждает проверку уникального script path, остановку child и ноль
   слушателей/owned processes при сохранённом QGIS на 9877.

   Уточнены [QGIS guidance](../../development/qgis.md) и
   [local-process cleanup](../../development/cleanup.md#temporary-local-processes):
   сравнивать порт/PID отвечающего экземпляра до запроса перезапуска и подтверждать
   очистку реального владельца сокета. Новый менеджер процессов не вводится:
   случай касался временного диагностического forward, не штатного launcher.

4. **Средний приоритет — избыточный вывод и неверный выбор session log.**
   Широкие пакетные чтения обрезались; raw JSONL может хранить целый вложенный
   transcript в одной строке. При поиске источника этой retro сначала был выбран
   guardian log, затем по parent id найден root с `source=vscode`.
   Для выборки использованы только нужные поля metadata и отдельные tool events
   до команды retro; исходные полные сессии в архив не копировались.
   [Acceptance guidance](../../development/acceptance.md) уже требует bounded
   summaries и ограниченные tails: это нарушение существующего порядка,
   а не повод дублировать его в AGENTS.md или создавать новый общий лог-CLI.

5. **Низкий приоритет — сетевой контекст локального Telegram-скрипта.**
   Первые уведомления останавливались при проверке бота в ограниченном процессе.
   Запрошенный пользователем тест и итоговое Send с сетевым доступом подтверждены
   Telegram API; токен читал только локальный скрипт. Код скрипта и профильные
   инструкции не меняются: причина была в режиме запуска, а не в токене.

Проверены `viewer/package.json`, Compose typecheck, `check-local.ps1` и
`.github/workflows/checks.yml`: проверки типов, viewer, документации и границ
уже подключены. Общего pre-commit hook нет; CI остаётся workflow_dispatch по
существующему решению. Новый guard использует эти entrypoints, автоматические
триггеры не добавлены. AGENTS.md, глобальные настройки и сторонние skills не
менялись; новые памятки размещены только в профильных ветках документации.

Пройдены 9/9 новых Node-тестов, CLI source preflight, Node syntax, синтаксис
изменённого PowerShell wrapper и ссылки изменённых документов. Первоначальный
запуск Node test runner в sandbox остановился на spawn EPERM до выполнения
тестов; тот же набор прошёл с разрешёнными локальными дочерними процессами.
QGIS, Docker, браузеры и сетевые сервисы не запускались; временные файловые
fixtures удаляются и проверяются в finally. Продуктовая приёмка №109 не
повторялась: приложение, desktop helper и service runner не меняются.
