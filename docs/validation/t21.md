# Опциональный TLS — №33

03.11.2026. Задача: [№33](https://github.com/stepanosokin/hmc-app-prototype/issues/33).
Исходный коммит: `17dbc78cb0672659bcbab6473890dafb4159f87b`.
Объём №33 выполнен: полная T5/T8-приёмка и полный TLS-сценарий прошли.

Отдельный Nginx 1.31.6 Alpine с фиксированным digest принимает HTTPS;
gateway сохраняет проверку API-ключей и задаёт внешний origin ссылок.
Override закрывает прежние порты gateway/viewer. Команды `tls-enable`,
`tls-check`, `tls-reload`, `start/stop/status` используют одну конфигурацию.
Порядок работы: [ADMIN](../../ADMIN.md#включить-https-tls), [TLS](../tls.md).

Новые проверки ограничены двумя согласованными границами: команды оператора
и реальные HTTPS-запросы. Старые обязательные регрессии T8/T5 сохранены.

Окружение: Windows, Node 26.10.0, Docker Engine 29.1.2,
Compose 2.40.3-desktop.1. Реальный GRIB:
`dddfd6c63ba73e5e7337c21e105f16417003429f8179a44ca58bb110cb43736a`.
Перед приёмкой зафиксированы 362 входа с размерами, SHA256 и копиями байтов;
изменённые runtime-файлы проверены против prospective Git filters и байтов индекса Git.

Ревью Standards: исправлены фиксация новых `.mjs`/`.conf`, журналы неудачного
запуска и права Linux-fixtures. Ревью Spec: проверка закрытого ключа перенесена
в proxy, исключены URL с секретами из request-context журнала Nginx,
API-токен читается контейнером без сохранения вывода. Открытых блокирующих
замечаний после повторного ревью нет.

Первая полная попытка `final1` прошла T5, T8 и suite (122 теста,
37 ожидаемых skips), но не прошла возврат сертификата: Nginx сохранил прежний
SSL-объект при совпадении inode/mtime. Короткий `probe2` воспроизвёл отказ;
`probe3` с единственным изменением `ssl_object_cache_inheritable off` прошёл
20 циклов замены/возврата (40 изменений сертификата). Директива добавлена
в рабочую конфигурацию, а существующий TLS-сценарий фиксирует одинаковые
timestamps файлов. Повторные Standards/Spec-ревью не нашли блокирующих замечаний.
`probe1` выявил только ошибку прав диагностической фикстуры и сохранён отдельно.
Повторная полная приёмка `final2` прошла.

После неё в тестовом инструменте устранено временное Docker-логирование
при чтении API-токена: отдельный контейнер использует `--log-driver none`,
`--network none`, UID 65532 и read-only mount; вывод не попадает в отчёт.
В `final3` повторён весь TLS-сценарий. Флаг `-Development` сократил только
подготовку T8: сам TLS-checker выполняет все сценарии без пропусков.
Сравнение двух полных снимков установило единственное изменение —
`tools/check-tls.mjs`, только получение тестового токена. Остальные 361 вход
и все сервисные образы совпали. Поэтому полные T5/T8/suite из `final2`
сохранены с собственными входами, а затронутая TLS-проверка принята на `final3`.

Неуспешные Development-попытки сохранены отдельно:

- `dev1`: повторный аргумент `nginx` при проверке конфигурации.
- `dev2`: временные каталоги Nginx в read-only файловой системе.
- `dev3`: проверка ожидала только 502 при допустимом 504 от недоступного gateway.
- `dev4`: сканер принял свой строковый литерал PEM-заголовка в снимке исходника
  за ключ; исправлен поиск реальных секретов и приватных фрагментов.

Для этих четырёх попыток подтверждён нулевой остаток контейнеров, томов и
сетей. Архивы: `HMC_EVIDENCE_ROOT/t21/dev1` … `t21/dev4`.
Копии проверены по размерам и SHA256; исходные отчёты сохранены.
CLI/документальные проверки не создавали Docker-ресурсов.
Архивы `final1` и `probe1` … `probe3` также сохранены; их ресурсы удалены.
