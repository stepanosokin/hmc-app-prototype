# Производные уровни отображения и сглаженная поверхность изолиний

02.11.2026 пользователь принял сравнение ×8 и сглаженную поверхность изолиний
из задач [№79](https://github.com/stepanosokin/hmc-app-prototype/issues/79) и
[№80](https://github.com/stepanosokin/hmc-app-prototype/issues/80), включая
отклонения значительно больше 1–2 экранных пикселей. Для обычной карты выбираем
×8: уменьшенные числовые блоки ускоряют заливку, изолинии и независимый слой ветра.
Автоматический выбор уровня по масштабу пока не вводится.

Это заменяет требование [ADR 0011](0011-native-browser-contours.md) строить все
изолинии непосредственно по нативным ячейкам. Перед marching squares браузер
сглаживает числовую поверхность Gaussian σ=1.2, radius=4 и положительным
кубическим B-spline с подразделением до ×4. Геометрия линий отдельно не
округляется и не сглаживается. Пропуски ограничивают фильтрацию; допустимые нули
сохраняются. Погрешность исходного float32-кодирования не является допуском
обобщения: положение линий и локальные экстремумы могут измениться.

[Контракт производного отображения](../../publication/display-pyramid.v1.json)
задаёт уровни ×2/×4/×8, равномерное покрытие исходного footprint, средние с весами
пересечения ячеек и консервативную маску. Производные блоки создаёт штатный API
по существующему Zarr по запросу, в ограниченном кеше; доступность публикации,
исходного хранилища и права проверяются до выдачи кеша. Первый запрос оплачивает
расчёт; постоянные пирамиды и повторное ingestion не требуются.

Исходные GRIB/Zarr/COG, редакции и канонические point/series/EDR/GIS сохраняются.
Native API версий 1–3 остаётся доступным; новый путь `/display/4/{factor}/`
отделяет производную сетку от идентичности исходного поля. Старые профили 1–2
продолжают отображаться по исходным блокам. Развёртывание: [№81](https://github.com/stepanosokin/hmc-app-prototype/issues/81).
